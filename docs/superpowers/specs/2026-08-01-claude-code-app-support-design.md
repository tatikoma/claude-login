# Поддержка Claude Code App в claude-login

Дата: 2026-08-01. Статус: согласовано, готово к плану реализации.

## Задача

Сейчас `claude-login` переключает аккаунты только для CLI. В настольном приложении Claude (вкладка **Code**) смена аккаунта делается логаутом и логином, и после этого пропадают все проекты и чаты — продолжить работу нельзя.

Нужно: переключать аккаунты для приложения так же, как для CLI; видеть и продолжать чаты, начатые под другим аккаунтом; выбирать цель запуска (CLI или App) и настраивать её в разделе настроек.

### Причина проблемы

Приложение хранит индекс сессий вкладки Code по пути

```
<userData>/claude-code-sessions/<accountUuid>/<orgUuid>/<sessionId>.json
```

Это буквально `path.join(userDataPath, "claude-code-sessions", currentAccountId, currentOrgId)` в классе `LocalSessionManager` (проверено чтением `app.asar` 1.24012.9). Вошли под другим аккаунтом — приложение смотрит в другой каталог и видит пустоту.

Сами диалоги при этом не теряются: в каждом файле сессии есть `cliSessionId`, а транскрипт лежит в `~/.claude/projects/<slug>/<cliSessionId>.jsonl` — то есть там же, где у CLI, и `claude-login` этот каталог уже шарит между профилями. **Пропадает индекс, а не история.**

### Опорные факты о приложении

Все проверены чтением `app.asar` или состоянием диска; помеченные «не проверено» подлежат проверке на реализации.

| факт | значение |
| --- | --- |
| `CLAUDE_USER_DATA_DIR` | при её наличии приложение делает `app.setPath("userData", <dir>)`, логи → `<dir>/Logs`. Прямой аналог `CLAUDE_CONFIG_DIR` |
| токен приложения | `<userData>/config.json`, ключи `oauth:tokenCacheV2` / `oauth:tokenCache`, зашифрованы Electron safeStorage (префикс `djEw` = `v10`), ключ в Keychain-элементе `Claude Safe Storage` |
| текущий аккаунт | `<userData>/config.json`, ключ `lastKnownAccountUuid` |
| логин App ≠ логин CLI | приложение — «хост» провайдера: сайдкару отдаются `CLAUDE_CODE_HOST_CREDS_FILE`, `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST=1`, `CLAUDE_CODE_HOST_AUTH_ENV_VAR`. Элемент `Claude Code-credentials` для сессий приложения не используется, `claude auth login` приложение не логинит |
| импорт CLI-сессии | IPC-метод `importCliSession(cliSessionId)`, валидирует UUID, читает транскрипт из `~/.claude/projects`, создаёт запись `local_<cliSessionId>`. В логах упоминается «deep-link import race» — внешний триггер существует, **форма ссылки не выяснена** |
| поля файла сессии | `sessionId`, `cliSessionId`, `cwd`, `originCwd`, `title`, `titleSource`, `model`, `effort`, `permissionMode`, `isArchived`, `createdAt`, `lastActivityAt`, `lastFocusedAt`, конфиг MCP |
| orgUuid | приложение берёт его из `GET /api/oauth/profile` → `organization.uuid` |
| второй экземпляр приложения | **проверено экспериментом:** запускается одновременно с уже открытым. Второй процесс с `CLAUDE_USER_DATA_DIR=<временный каталог>` поднялся рядом с работающим (свои renderer-хелперы, свой `config.json` меньше чем за секунду), первый не пострадал. Single-instance-замка нет |
| каталог сессий до логина | **проверено:** `claude-code-sessions` в свежем каталоге данных не создаётся — он появляется только после того, как приложение разрешит аккаунт и организацию. Поэтому ленивая адопция — основной путь |
| размеры | весь каталог ~13 ГБ (кеши, VM-бандлы), из них сессии 5,3 МБ + 30 МБ, сайдкар-CLI 249 МБ |

## Принятые решения

1. **Профиль данных приложения на аккаунт** через `CLAUDE_USER_DATA_DIR`. Логаут не нужен: каждый аккаунт остаётся залогиненным в своём каталоге, переключение — это запуск приложения из `claude-login`.
2. **Плоский общий пул сессий.** Листовой каталог `claude-code-sessions/<accountUuid>/<orgUuid>` в каждом профиле — симлинк на один пул. Приложение читает и пишет прямо в пул, синхронизировать нечего. Отклонены: симлинк на уровне `<accountUuid>` (не сливает аккаунты разных организаций) и копирование между каталогами (дубликаты, гонки, отставание).
3. **Существующий системный каталог приложения = профиль `default`**, как `~/.claude` для CLI. Его чаты втягиваются в пул, перед первым переносом делается копия каталогов сессий.
4. **Цель запуска настраивается**, CLI остаётся по умолчанию: свежая установка ничего не меняет в поведении — тот же принцип, что у `launchArgs`.
5. **Общее между профилями приложения:** пул сессий, тяжёлые бинари и расширения с MCP. `config.json` не шарится никогда — в нём токен.
6. **Флагов запуска у приложения нет.** `model`/`effort`/`permissionMode` живут в файле сессии, и приложение помнит последний выбор. Поскольку каталог данных теперь на аккаунт, эти настройки автоматически становятся раздельными. Вместо флагов в настройках App — список переменных окружения запуска. Дописывать дефолты в файлы сессий приложения не будем: это реверс, который сломается на обновлении.

## Архитектура

### Модули

Новый `claude_login/claude_app.py` держит **всё** знание о приложении — по образцу `claude_cli.py`: путь к бандлу, раскладку каталога данных, формулу `claude-code-sessions/<acct>/<org>`, чтение файлов сессий, состояние логина, сборку окружения и запуск процесса. `commands.py` про внутренности приложения не знает ничего.

Изменения в существующих модулях:

| модуль | что добавляется |
| --- | --- |
| `store.py` | `Profile.app_data_dir`, `Profile.org_uuid`; ключи реестра `launchTarget`, `appShared`, `appEnv`, `appSessionsShared`; `Vault.app_dir_for`, `link_app_shared`, `wire_session_pool`, `app_shared_conflicts` |
| `commands.py` | выбор цели запуска, `launch_app`, секции настроек, `cmd_app*`, App-строки в `doctor` |
| `cli.py` | флаги `--app` / `--cli`, подкоманда `app` с `adopt` / `relink` / `status` |
| `usage.py` | `fetch_org_uuid(profile)` — живёт здесь, потому что нужен транспорт и обновление токена, которые уже тут |
| `errors.py` | `ClaudeAppError` |

### Раскладка на диске

```
~/.claude-accounts/
├── accounts.json                 + launchTarget, appShared, appEnv, appSessionsShared
├── app-shared/
│   ├── ccd-sessions/             ← плоский пул чатов вкладки Code
│   ├── agent-sessions/           ← пул agent-mode
│   └── .backup-<ms>/             копия каталогов сессий перед первым переносом
└── profiles/<name>/
    ├── …                         как сейчас: .claude.json + симлинки в ~/.claude
    └── app-data/                 ← CLAUDE_USER_DATA_DIR этого аккаунта
        ├── config.json                                    свой, с токеном — не общий
        ├── claude-code            -> <системный каталог>/claude-code
        ├── claude-code-vm         -> …
        ├── vm_bundles             -> …
        ├── Claude Extensions      -> …
        ├── Claude Extensions Settings -> …
        ├── extensions-installations.json -> …
        ├── claude_desktop_config.json    -> …
        ├── git-worktrees.json     -> …
        ├── claude-code-sessions/<acct>/<org>      -> app-shared/ccd-sessions
        └── local-agent-mode-sessions/<acct>/<org> -> app-shared/agent-sessions
```

Источник общего — системный `~/Library/Application Support/Claude`. Он же профиль `default` приложения: как и `~/.claude`, не переносится и не удаляется, но получает симлинки своих каталогов сессий в пул.

**Никогда не общие:** `config.json`, `Local State`, `Cookies*`, `Session Storage`, `Local Storage`, `IndexedDB`, `Partitions`, `WebStorage`, `sentry`, `plan-usage-history.json`, все `*Cache*`.

Список общего лежит в реестре (`appShared`), как `shared` для CLI, и правится руками с последующим `claude-login app relink`.

### Как определяется `<acct>/<org>`

Три источника по порядку:

1. **Каталог уже есть в профиле** — приложение его создало. Берём имена как есть.
2. **Реестр + API.** `accountUuid` в реестре уже есть; `orgUuid` докладываем через `usage.fetch_org_uuid` (`GET /api/oauth/profile`) и кешируем в профиль.
3. **Ленивая адопция.** Ничего не известно — ссылку не ставим, приложение создаст каталог само. При следующем обращении (`app relink`, следующий запуск, `doctor`) утилита увидит непривязанный каталог, перенесёт содержимое в пул и поставит симлинк. Первый запуск под новым аккаунтом покажет пустые Recents, дальше всё общее.

Ленивая адопция — не аварийный путь, а штатный: она же вычищает каталоги, созданные приложением в обход нас.

### Поток запуска

```
cmd_use / interactive
  └ resolve target: --app/--cli → launchTarget из реестра → "cli"
  ├─ target == cli:  как сейчас, вплоть до execve
  └─ target == app:
       ├ claude_app.find_app()                бандл на месте?
       ├ ensure_app_profile(profile)          mkdir app-data (0700), link_app_shared, wire_session_pool
       ├ adopt_orphan_dirs()                  ленивая адопция в пул
       ├ app_status(profile)                  signed-in / logged-out / чужой аккаунт
       ├ vault.touch(profile); save()
       ├ печать: аккаунт, каталог данных, состояние логина, последняя сессия в этом каталоге
       └ Popen(binary, env=…, start_new_session=True) и выход 0
```

`Popen` с `start_new_session=True`, а не `os.execve`: GUI не должен умирать вместе с терминалом. Не `open -a`: он не передаёт переменные окружения. `stdout`/`stderr` приложения уходят в `/dev/null`, чтобы не засорять терминал.

Окружение дочернего процесса: текущее + `CLAUDE_USER_DATA_DIR=<app-data>` + `appEnv`, минус `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` (та же чистка, что в `claude_cli.child_env`) и минус `CLAUDE_CONFIG_DIR` — приложение и его сайдкар должны работать с общим `~/.claude`, иначе транскрипты уедут из общего каталога.

### Состояние логина в приложении

`claude_app.app_status(dir)` → `signed-in` | `logged-out` | `missing`, плюс `account_uuid` из `lastKnownAccountUuid`. Определяется по **наличию** ключей `oauth:tokenCacheV2` / `oauth:tokenCache` в `config.json`; расшифровка не нужна и не делается.

Если `lastKnownAccountUuid` не совпадает с `accountUuid` профиля — предупреждение: в этом каталоге залогинен другой аккаунт. Показывается в `doctor` и перед запуском.

Первый запуск профиля App покажет экран логина приложения. Это неизбежно и не то же самое, что `claude auth login`, — печатаем об этом явно, один раз на профиль.

### Continue для App

После переключения пул уже содержит сессии прошлого аккаунта, и Recents показывают их сверху — то есть продолжение доступно в один клик. Сверх этого:

- `claude_app.last_session(pool, cwd)` находит в пуле самую свежую незаархивированную сессию для каталога (`lastFocusedAt`, иначе `lastActivityAt`) и `claude-login` печатает её заголовок перед запуском — чтобы не искать глазами.
- Автооткрытие оставляем надстройкой: проверить, открывает ли приложение последнюю сфокусированную сессию само, и есть ли пригодная deep-link-форма. Если да — появляется настройка `Continue last chat`; если нет — настройки нет, остаётся печать. **Не блокирует остальное.**

### Настройки

`cmd_settings` становится двухуровневым: верхний экран — разделы, Enter уводит в подэкран. Так расширяемо и не сваливает всё в один список.

```
Settings

           SETTING                              VALUE
❯ Launch target            CLI
  Launch flags (CLI)       --dangerously-skip-permissions --effort max
  Claude Code App          per-account · chats shared · 8 shared entries

↑↓ move · ⏎ open · q back
```

`Launch target` перебирается на месте: `CLI → App → ask`. При `ask` Enter в списке аккаунтов сначала спрашивает цель, и только потом запускает. `Launch flags (CLI)` — существующий экран без изменений. Подэкран App:

```
Settings — Claude Code App

claude-login launches /Applications/Claude.app under the selected account

           SETTING                       VALUE
❯ Per-account app profile   on
  Share chats & projects    on
  Shared entries            8 entries          edit
  Launch env                2 variables        edit
  App path                  /Applications/Claude.app
```

Смысл переключателей подэкрана:

- `Per-account app profile` — `off` возвращает старое поведение: приложение запускается с системным каталогом данных, без `CLAUDE_USER_DATA_DIR`. Полезно, чтобы сравнить или откатиться, не разбирая раскладку.
- `Share chats & projects` — `off` оставляет каждому профилю свой каталог сессий: симлинки на пул не ставятся, уже поставленные снимаются с возвратом содержимого. То есть переключатель обратим в обе стороны.

В списке аккаунтов: `⏎` — цель по умолчанию, `o` — «открыть в другой цели». Одна клавиша вместо захода в настройки — это и есть удобство в ежедневном использовании.

### Поверхность командной строки

```
claude-login work --app                запустить App под аккаунтом
claude-login work --cli                принудительно CLI
claude-login app                       состояние App-профилей (таблица)
claude-login app adopt [--dry-run]     втянуть существующие чаты в пул (с бэкапом)
claude-login app relink [--force]      пересоздать общее и ссылки на пул
```

`--app` и `--cli` — булевы, поэтому в `cli._VALUE_FLAGS` не попадают. Объявляются и в корневом парсере, и в `use` с `default=argparse.SUPPRESS`, иначе подпарсер затрёт значение корневого.

### Миграция существующих чатов

`claude-login app adopt`, он же вызывается автоматически при первом запуске App-цели:

1. Копия `claude-code-sessions` и `local-agent-mode-sessions` из системного каталога в `app-shared/.backup-<ms>/` (35 МБ).
2. Содержимое всех `<acct>/<org>` переносится в плоский пул. Коллизия имён файлов практически невозможна (uuid); при коллизии остаётся более свежий по `lastActivityAt`, второй уходит в `.backup-<ms>/collisions/`, печатается note.
3. На месте каждого `<acct>/<org>` — симлинк на пул.
4. `--dry-run` печатает план и не трогает ничего.

Сессии переносятся, пока их никто не пишет, поэтому живой процесс приложения имеет значение — но вести себя надо по-разному в двух путях:

- **Явный `app adopt`** — если приложение запущено, отказ с просьбой его закрыть. `--force` не предусмотрен.
- **Автоматический перенос при запуске App-цели** — если приложение запущено, перенос **пропускается** с заметкой «чаты станут общими после `claude-login app adopt` с закрытым приложением», а запуск продолжается. Отказывать в запуске из-за миграции нельзя: это ежедневная операция.

Ленивая адопция каталога, который приложение создало само, живёт по тому же правилу.

## Обработка ошибок

| ситуация | поведение |
| --- | --- |
| бандл приложения не найден | `ClaudeAppError` с путём и подсказкой про `CLAUDE_LOGIN_APP_PATH` |
| в профиле App разошедшаяся копия общего файла | как в `link_shared`: молча перелинковать при побайтовом совпадении, иначе сообщить как конфликт; `--force` уносит в `.shadowed/` |
| `orgUuid` неизвестен (нет сети, не логинились) | не ошибка: ленивая адопция + note |
| в каталоге профиля залогинен другой аккаунт | warn с обоими UUID; запуск не блокируется |
| приложение запущено при `app adopt` | отказ, просьба закрыть приложение |
| пул недоступен (права) | попадает в список конфликтов, как у `link_shared` |
| цель `app` на не-macOS | `ClaudeAppError`: приложение только для macOS в рамках этой задачи |

## Тесты

Один файл `tests/test_claude_login.py`, как принято в проекте. Заглушка приложения `FAKE_APP` — питоновский скрипт по образцу `FAKE_CLAUDE`: пишет `config.json` с ключом токена и создаёт `claude-code-sessions/<acct>/<org>`, чтобы проверялась адопция. Системный каталог приложения подменяется патчем `claude_app.default_app_support_dir` (и env-переменной `CLAUDE_LOGIN_APP_SUPPORT` для ручных экспериментов) — реальный каталог пользователя тесты не трогают.

- `TestAppProfile` — создаётся `app-data` с правами `0700`; общее симлинкуется; `config.json` не симлинкуется никогда; повторный вызов идемпотентен.
- `TestSessionPool` — существующие `<acct>/<org>` переносятся в пул; на их месте симлинк; бэкап создан; `--dry-run` не меняет ничего; коллизия имён разрешается по `lastActivityAt`; разошедшийся каталог не затирается; ленивая адопция подхватывает каталог, созданный приложением.
- `TestAppLaunch` — окружение содержит `CLAUDE_USER_DATA_DIR` и `appEnv`, не содержит `CLAUDE_CONFIG_DIR` и ambient-токенов; процесс запускается отсоединённым (`Popen` мокается); отказ, когда бандла нет.
- `TestLaunchTarget` — `--app`/`--cli` перебивают `launchTarget`; дефолт `cli`; `o` в списке выбирает другую цель.
- `TestAppStatus` — `signed-in`/`logged-out`/`missing` по ключам `config.json`; несовпадение `lastKnownAccountUuid` даёт предупреждение.
- `TestAppContinue` — последняя сессия для каталога находится по `lastFocusedAt`, при его отсутствии по `lastActivityAt`; заархивированные пропускаются.

Существующие 100 тестов должны остаться зелёными без правок — поведение CLI не меняется.

## Что осознанно не делаем

- Не расшифровываем и не подменяем токен приложения. Опора на внутренний формат safeStorage не нужна: `CLAUDE_USER_DATA_DIR` решает задачу без этого.
- Не навязываем приложению `model`/`effort`/`permissionMode`.
- Не шарим `config.json` целиком ни в каком виде.
- Не поддерживаем вариант сборки «3p» (`userData + "-3p"`, `configLibrary/<uuid>.json`) — он для managed-развёртываний и на основной путь не влияет.
