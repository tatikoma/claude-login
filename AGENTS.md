# claude-login

Переключение между несколькими аккаунтами Claude Code с одной машины. Python 3.9+, только стандартная библиотека, ноль зависимостей.

**Язык:** код, докстринги и комментарии — английские. Документация (`README.md`, этот файл) — русская. Не смешивать.

---

## Что это за продукт

Утилита, которая держит по одному изолированному «профилю» на каждый аккаунт Claude Code и запускает настоящий `claude` под выбранным. Основной сценарий: закончились лимиты у одного аккаунта — переключился на другой, продолжил ту же работу, потому что история диалогов, настройки, скиллы и плагины остаются общими.

Логинит пользователя настоящий `claude auth login`; он же пишет и читает токены. Утилита только подставляет ему другой `CLAUDE_CONFIG_DIR`.

**Чего продукт НЕ делает** — это регулярно приписывают, и агент начинает искать несуществующий код:

- Не имеет своего OAuth-клиента и своего хранилища секретов. Нигде не реализован ни браузерный флоу, ни PKCE. Единственное место, где токен проходит через наш код, — обновление протухшего access-токена (`usage._refresh`) и перенос Keychain-элемента при переименовании (`store.move_config_dir`).
- Не обходит и не суммирует лимиты. Колонки `5H`/`WEEK` — это чтение `GET /api/oauth/usage`, тот же эндпоинт, что за `/usage` внутри сессии.
- Не переключает уже запущенную сессию `claude`. Переключение действует только на новые запуски: мы делаем `execve`, а не что-то с работающим процессом.
- Не навязывает настольному приложению модель, `effort` и режим разрешений: у приложения нет флагов запуска, эти настройки живут в файле каждой сессии. Соответственно нет и «флагов для App» — есть список переменных окружения.
- Не расшифровывает и не подменяет токен приложения. Профили приложения разводятся каталогом данных, а не работой с safeStorage.
- Не имеет ни линтера, ни типчекера в оснастке, ни CI, ни `.git`. Каталог — распакованный архив (`claude-login-main`), истории коммитов нет.

## Команды

```bash
./bin/claude-login                 # запуск прямо из каталога, без установки
./install.sh                       # симлинки claude-login и ccl в ~/.local/bin
./install.sh --pipx                # или изолированной pipx-программой
./install.sh --uninstall           # снять симлинки

python3 -m unittest discover -s tests            # ← обязательно после любой правки
CLAUDE_LOGIN_INTEGRATION=1 python3 -m unittest discover -s tests   # + 2 канарейки на живой Keychain

claude-login doctor                # диагностика: путь к claude, Keychain, сроки токенов, битые линки, состояние App
claude-login list --json           # машиночитаемое состояние, удобно для отладки
claude-login app                   # состояние профилей приложения
claude-login app adopt --dry-run   # что переехало бы в общий пул чатов
claude-login app link              # связать аккаунт с пулом, не запуская приложение
claude-login app open              # открыть приложение под выбранными аккаунтами
claude-login sync-all              # раздать скиллы, MCP и чаты между аккаунтами
claude-login setup                 # онбординг на новой машине
```

Пометки, из-за которых это стоит читать:

- **Тесты — единственная автоматика в проекте.** Линтера, `mypy` и CI нет; всё, что enforced, enforced тестами. `python3 -m unittest discover -s tests` сейчас даёт `Ran 253 tests ... OK (skipped=2)` за ~46 с.
- Пропущенные два теста — `TestKeychainIntegration`. Они пишут фиктивный токен в **настоящий** Keychain и дёргают настоящий `claude`. Запускать осознанно, не в общем прогоне.
- Юнит-тесты никогда не касаются реальных аккаунтов: `Base.setUp` подменяет `claude` на питоновскую заглушку (`FAKE_CLAUDE`) через `CLAUDE_LOGIN_CLAUDE_BIN`, `~/.claude` — на временный каталог через патч `claude_cli.default_config_dir`, а `CLAUDE_LOGIN_KEYCHAIN_PREFIX` — на уникальный для прогона. Последнее обязательно: подмены каталога мало, потому что у `config_dir=None` имя Keychain-элемента фиксированное (`Claude Code-credentials`), и на залогиненной машине `bootstrap` усыновлял живой машинный аккаунт как профиль `default` — три теста на подсчёт аккаунтов падали ровно у того, кто пользуется утилитой. Для приложения то же делает `_AppBase`: `CLAUDE_LOGIN_APP_SUPPORT` на временный каталог, `CLAUDE_LOGIN_APP_PATH` на фиктивный бандл, а `claude_app.launch`/`is_in_use` патчатся. **Настоящий каталог приложения не трогается ни одним тестом** — если добавляете тест про App, наследуйтесь от `_AppBase`.
- `claude-login list` печатается один раз и потому ждёт сеть (таймаут 6 с). Интерактивный список — нет, он рисуется сразу и подставляет цифры позже. Для офлайна и скорости — `--no-usage`.
- В `pyproject.toml` `requires-python = ">=3.9"`. Не использовать синтаксис новее: аннотации вида `str | None` допустимы только потому, что в каждом модуле есть `from __future__ import annotations`.

## Архитектура

Один пакет, семь содержательных модулей. Границы жёсткие — не размывать:

| модуль | отвечает за | не делает |
| --- | --- | --- |
| `cli.py` | argparse, алиасы, `split_args` | ничего не знает про Keychain и файлы |
| `commands.py` | реализация всех подкоманд, слои флагов, выбор цели запуска, интерактивный цикл | не парсит argv, не рисует таблицы сам |
| `store.py` | реестр `accounts.json`, каталоги профилей, симлинки, пул чатов приложения, статусы | не знает про терминал |
| `claude_cli.py` | **всё** знание про бинарник `claude` и его раскладку на диске | не принимает решений |
| `claude_app.py` | **всё** знание про настольное приложение: бандл, каталог данных, статус логина, чтение файлов сессий, запуск | не трогает реестр |
| `keychain.py` | обёртка над `security(1)` | ничего кроме generic-password |
| `usage.py` | HTTP к API лимитов, обновление токена, отрисовка колонок | не пишет в реестр |
| `ui.py` | цвет, таблицы, промпты, относительное время | не читает клавиши |
| `picker.py` | сырой режим терминала, стрелки, отрисовка списка | не знает, что за данные показывает |
| `scripts/*.command` | кликабельные обёртки для Finder | **никакой логики** — только `cd` и вызов подкоманды |

Путь запуска, если читать сверху вниз:

```
cli.main
  └ cli.split_args        нормализует argv: `claude-login work` → `use work`, «--» → passthrough в claude
  └ argparse              → args.func или commands.interactive
      └ commands.bootstrap        первый запуск: регистрирует ~/.claude как профиль "default"
      └ picker.pick / cmd_*       выбор или прямая команда
      └ commands.build_claude_args  три слоя флагов
      └ claude_cli.exec_claude    execve — процесс замещается, дальше кода нет
```

**Источник истины:**

- Состояние утилиты — `~/.claude-accounts/accounts.json` (ключи `profiles`, `shared`, `launchArgs`, `lastUsed`, `defaultHidden`). Секретов там нет никогда.
- Аккаунт и его токены — на стороне Claude Code: `oauthAccount` в `.claude.json` профиля и элемент Keychain. Поля `email`/`accountUuid`/`subscriptionType` в реестре — **кеш**, обновляется через `Vault.refresh_identity`.
- Раскладка Claude Code на диске — только `claude_cli.py`. Если Claude Code сменит схему, править надо там и нигде больше.

### Механизм, на котором всё держится

Claude Code берёт и конфиг, и креды из `CLAUDE_CONFIG_DIR`:

| что | без переменной | с `CLAUDE_CONFIG_DIR=<dir>` |
| --- | --- | --- |
| конфиг | `~/.claude.json` | `<dir>/.claude.json` |
| Keychain (macOS) | `Claude Code-credentials` | `Claude Code-credentials-<sha256(NFC(dir))[:8]>` |
| fallback-файл | `~/.claude/.credentials.json` | `<dir>/.credentials.json` |

Приоритет конфига: если рядом есть `<dir>/.config.json` — используется он, иначе `.claude.json` (`claude_cli.global_config_path`). Это поведение сверено с кодом внутри настоящего бинарника, а не только с документацией.

Общее между профилями — симлинками из `~/.claude` (список в `store.DEFAULT_SHARED` и в ключе `shared` реестра). `.claude.json` симлинком быть не может: в нём и общее (доверенные папки, `mcpServers`, онбординг), и сам аккаунт (`oauthAccount`), — поэтому общая половина **копируется** (`seed_config`) и подтягивается по требованию (`sync_config`, оно же `claude-login sync`).

## Инварианты

Нарушаются тихо, ломают неочевидно:

1. **Любая запись в реестр — внутри `with vault.locked():` и заканчивается `vault.save()`.** Блокировка (`fcntl.flock` на `.registry.lock`) сериализует read-modify-write между параллельными запусками. Запись без локи затрёт чужую.
2. **`Vault.load()` мемоизирует.** После записи, которую сделал кто-то другой (или наш же `locked()`-блок), читать через `vault.reload()`. Иначе получите старые данные — на этом легко построить гонку.
3. **`claude_cli.exec_claude` — терминальная операция.** После неё кода нет и быть не может: процесс замещён. Всё, что нужно записать (`vault.touch`), пишется до.
4. **Кеш кредов надо инвалидировать.** `claude_cli.read_credentials` мемоизирует блоб на весь процесс (каждое чтение Keychain — это ~25 мс подпроцесса `security`). Любое изменение кредов обязано вызвать `forget_credentials(...)`; `login`/`logout`/`write_credentials`/`delete_credentials` это уже делают.
5. **Профиль `default` — это `~/.claude`, у него `config_dir is None`.** Его нельзя переименовать, нельзя удалить (`remove` только скрывает через `defaultHidden`), `prune` его не трогает никогда, симлинки в него не ставятся. Проверка — `profile.is_default`.
6. **Имя Keychain-элемента выводится из пути.** Переименование профиля обязано идти через `Vault.move_config_dir`, которая перекладывает секрет под новое имя и удаляет старое. Простой `rename()` каталога осиротит креды.
7. **`oauthAccount` не трогаем никогда.** Ни `seed_config`, ни `sync_config`, ни что-либо ещё не имеет права его переписать: это и есть привязка профиля к аккаунту.
8. **Слои флагов: `launchArgs` (реестр) → `extraArgs` профиля → то, что набрал пользователь.** Правый слой выбивает левый по имени флага; `-c`/`-r` считаются теми же флагами, что `--continue`/`--resume` (`FLAG_ALIASES`). Логика в `commands.build_claude_args` и `_flag_groups` — флаг и его значение всегда путешествуют вместе.
9. **Токены не печатаются никуда и ни в каком виде.** `list`, `doctor`, `--json` показывают только статус и сроки. Реестр — `0600`, каталоги хранилища — `0700`.
10. **Секрет уходит в `security(1)` через stdin**, не через argv, иначе он виден в `ps`. Откат на argv — только для блоба длиннее `_STDIN_LIMIT = 4032`, ровно как у самого Claude Code.
11. **Обновление токена — только когда он реально истёк** (`usage._token_for`, запас `REFRESH_MARGIN_MS`). Валидный access-токен используется как есть, чтобы не устроить гонку с работающей сессией.
12. **Лимиты не кешируются между запусками сознательно.** Не получилось запросить — рисуем `—`. Показать `4%`, когда лимит на самом деле выбран, хуже, чем не показать ничего.

## Ловушки

Формат: симптом → причина → что делать.

- **Симлинк на общий файл превратился в отдельный файл.** Claude Code пишет конфиги атомарно (во временный файл рядом + `rename`), а `rename` заменяет саму ссылку. Спасает то, что Claude Code резолвит путь до реального файла перед записью, — но сторонний редактор или ручной `cp` ссылку порвут. Диагностика — `doctor` (`diverged`), лечение — `relink` (молча вернёт ссылку, если копия побайтово совпадает) или `relink --force` (уберёт разошедшуюся копию в `<профиль>/.shadowed/`). Без `--force` чужие данные не трогаются никогда. На это поведение есть канарейка `test_claude_resolves_symlinks_before_writing_settings` — если будущая версия Claude Code перестанет резолвить путь, она это поймает.
- **Хардлинки вместо симлинков не работают.** Первая же атомарная запись из профиля разрывает связь (у профиля новый inode), а каталоги хардлинком не связать вообще. Проверено на живом бинарнике; не «оптимизировать» обратно.
- **`claude --continue` без транскрипта не начинает новую сессию, а прерывает запуск** с `No conversation found to continue`. Поэтому `build_claude_args` снимает флаг, если для текущего каталога нет непустого транскрипта (`claude_cli.has_transcript`), и снимает его же, если явно передан `--resume`. Имя каталога транскриптов вычисляется по правилу Claude Code: все не-алфанумерики → `-`, путь длиннее 200 символов обрезается и получает хвост-хеш (`project_dir_name`, `_legacy_hash36`).
- **Добавили новый флаг самой утилиты, который принимает значение, — обязательно допишите его в `cli._VALUE_FLAGS`.** Сейчас там пустое множество, потому что все флаги булевы. `split_args` идёт по argv до первого не-флага и считает его командой; без записи в `_VALUE_FLAGS` значение флага будет принято за имя аккаунта.
- **`--no-flags` и `--no-usage` объявлены с `default=argparse.SUPPRESS`** и в корневом парсере, и в подпарсерах. Это не украшение: без SUPPRESS подпарсер затрёт значение, которое уже прочитал корневой, и `claude-login --no-flags work` перестанет работать. Читать их только через `getattr(args, ..., False)`.
- **`argparse.REMAINDER` оставляет ведущий `--`.** `cli.main` его срезает — новые места с passthrough должны делать то же.
- **`link_shared` молча пропускает то, чего нет в `~/.claude`.** Это не баг: список `shared` — потенциальный. На живой машине половина записей (`CLAUDE.md`, `commands`, `agents`, `workflows`, `output-styles`, `rules`, `hooks`) обычно отсутствует, и в профиле появляются симлинки только на существующее. Не «исправлять» на создание пустых каталогов.
- **`picker` работает с `/dev/tty` напрямую и в сыром режиме.** Клавиши читаются по одному байту: чтение фиксированным куском проглотит и потеряет то, что пользователь набрал следом. `q`, `Ctrl-C`, `Ctrl-D`, а также одиночный `Esc` — выход; `j`/`k` дублируют стрелки. Без TTY есть откат на нумерованный промпт (`_pick_fallback`) — не сломать его при доработках.
- **Ни одна строка кадра `picker` не имеет права быть шире окна.** Перерисовка — это «курсор вверх на N строк», а перенос, сделанный самим терминалом, в этот счёт не попадает: кадр начинает наезжать на себя, и список превращается в кашу. Поэтому `_layout` знает ширину (`ui.terminal_width`) и укладывается в неё сам, в таком порядке: зазор между колонками с двух пробелов до одного (`GAPS`) → обрезка первой колонки, имени, до `MIN_COLUMN` → обрезка самой широкой из остальных → `ui.truncate` строки целиком как последний рубеж. Первой жертвует именно имя: аккаунт узнаётся по началу, а `98% ⟳ 05.08 01:00 · Fa…` не значит уже ничего. Подсказки внизу не режутся, а сворачиваются на несколько строк (`_wrap_hints`) — их число мы всё равно знаем. Регрессия закрыта `TestPickerLayout`.
- **`prune` без `--yes` всегда сначала показывает список.** Никаких «удалю по-тихому»: пользователь теряет логины.
- **`--app` и `--cli` — единственные флаги, которые распознаются после имени аккаунта.** Их поднимает влево `cli.hoist_target_flags`, потому что у `claude` таких флагов нет и passthrough означал бы гарантированную ошибку запуска. Escape-hatch — `claude-login work -- --app`. Новые флаги утилиты по умолчанию так себя вести не должны: правило «после имени всё уходит в claude» остаётся.
- **Не заменять `http.client` на `urllib.request` в `usage.py`.** Сборка цепочки обработчиков на каждый вызов стоила дороже самого запроса (410 → 275 мс на трёх аккаунтах). Asyncio там тоже уже мерили — не даёт ничего, 73 % времени составляет ответ сервера.

## Словарь домена

| термин | что это |
| --- | --- |
| **профиль** | каталог `~/.claude-accounts/profiles/<name>`, который отдаётся `claude` как `CLAUDE_CONFIG_DIR`. Имя каталога = обычно email аккаунта |
| **vault / реестр** | `~/.claude-accounts` и его `accounts.json` |
| **default** | не отдельный каталог, а машинный `~/.claude` (`config_dir is None`) |
| **shared** | записи, которые симлинкуются из `~/.claude` в каждый профиль |
| **seed** | однократное копирование общей половины `~/.claude.json` в новый профиль |
| **sync** | повторное копирование её же в существующий профиль; `projects` при этом **сливается**, а не затирается |
| **relink** | пересоздание симлинков; **diverged** — профиль обзавёлся своей копией общего файла; **shadowed** — куда `relink --force` убирает такую копию |
| **launchArgs / extraArgs / passthrough** | три слоя флагов: общий из реестра, персональный у профиля, набранный в командной строке |
| **цель запуска (target)** | `cli`, `app` или `ask` — куда уходит выбранный аккаунт |
| **пул** | общий каталог чатов приложения (`app-shared/ccd-sessions`), на который смотрят все профили |
| **adopt** | однократный перенос уже существующих чатов приложения в пул |
| **машинный каталог приложения** | `~/Library/Application Support/Claude` — источник общего для App и профиль `default`, аналог `~/.claude` |
| **статусы профиля** | `ok`, `expiring` (refresh-токен ближе `EXPIRY_WARNING_DAYS`), `expired`, `logged-out` (каталог есть, кредов нет — обычно прерванный `add`), `missing` (каталог удалён руками); плюс `orphan` — каталог без записи в реестре |
| **окна лимитов** | `five_hour`, `seven_day` (в UI — `5H`, `WEEK`) и `weekly_scoped` — лимит на конкретную модель. Последний показывается только когда он строже общего |

## Конвенции

Enforced нет ничем, кроме тестов, — поэтому соблюдать руками:

1. **Ноль зависимостей.** `dependencies = []` в `pyproject.toml` — это фича, а не недоделка. `certifi` подхватывается опционально, если он уже есть в системе (`usage._certifi_bundle`), но требовать его нельзя.
2. **Комментарий объясняет «почему», а не «что».** В проекте выдержан один стиль: докстринг модуля — зачем модуль существует; докстринг функции — контракт и подводные камни; строчный комментарий — только там, где очевидное решение неверно. Не добавлять комментариев, пересказывающих код.
3. Модель данных — `@dataclass` (`Profile`, `Status`, `Window`, `Usage`, `Item`, `Result`, `Action`). Сериализация — методы `to_json`/`from_json` с camelCase в JSON и snake_case в Python.
4. Ошибки — только подклассы `ClaudeLoginError` из `errors.py`; у каждого свой `exit_code`. `cli.main` печатает их как `error: <текст>` без трейсбека. Не выбрасывать наружу голые `OSError`.
5. Тексты сообщений — строчными, без точки в конце, с подсказкой, что делать (`... — run \`claude-login list\``). Вывод — только через `ui.*`, не через `print` напрямую (кроме уже существующих `ui.info`/таблиц).
6. Атомарная запись файлов — через `tempfile.mkstemp` в том же каталоге + `chmod(0o600)` + `os.replace`, с удалением temp-файла в `except BaseException`. Скопировать существующий паттерн (`Vault.save`, `_write_global_config`, `write_credentials`), а не изобретать.
7. Новая логика — новый тест. 253 теста — это заданная планка, а не случайность.

## Claude Desktop App

Поддержка приложения реализована: `claude-login work --app` запускает
`/Applications/Claude.app` под выбранным аккаунтом, а чаты вкладки Code остаются
общими между аккаунтами. Спека — `docs/superpowers/specs/2026-08-01-claude-code-app-support-design.md`,
план — `docs/superpowers/plans/2026-08-01-claude-code-app-support.md`.

Механизм в двух предложениях. Каждому аккаунту достаётся свой каталог данных
приложения через `CLAUDE_USER_DATA_DIR` (`profiles/<имя>/app-data`), поэтому
логаут не нужен и окна двух аккаунтов работают одновременно. Листовой каталог
`claude-code-sessions/<accountUuid>/<orgUuid>` в каждом профиле — симлинк на один
пул `app-shared/ccd-sessions`, поэтому Recents одинаковы под любым аккаунтом.

Раскладка приложения — `~/Library/Application Support/Claude/`:

| путь | что это |
| --- | --- |
| `config.json` | настройки приложения; там же **токен аккаунта** под ключами `oauth:tokenCacheV2` / `oauth:tokenCache` и `lastKnownAccountUuid` |
| `claude-code-sessions/<accountUuid>/<orgUuid>/<sessionId>.json` | **индекс сессий вкладки Code — то самое, что «пропадает»** |
| `local-agent-mode-sessions/<accountUuid>/<orgUuid>/` | то же для agent-mode |
| `claude-code/<version>/claude.app` | CLI, который приложение качает и запускает как сайдкар |
| `plan-usage-history.json` | история расхода лимитов |

Факты, на которых всё держится. Прочитаны в коде `/Applications/Claude.app/Contents/Resources/app.asar` (бандл 1.24012.9, встроенный claude-code 2.1.219) или проверены на этой машине:

- **Индекс сессий приколочен к аккаунту.** `getStorageDir()` в классе `LocalSessionManager` — это буквально `path.join(userDataPath, "claude-code-sessions", currentAccountId, currentOrgId)`, и он возвращает `null`, пока аккаунт и организация не разрешены. Отсюда симптом «пропали чаты».
- **Каталог сессий появляется только после логина** — проверено экспериментом на свежем каталоге данных. Поэтому `wire_session_pool` обязан работать лениво: первый запуск нового профиля пула ещё не имеет, второй уже да.
- **Транскрипты диалогов общие и лежат там же, где у CLI.** Проверено эмпирически: `cliSessionId` из файла сессии приложения находится как `~/.claude/projects/<slug>/<cliSessionId>.jsonl`. Приложение — UI над теми же транскриптами, которые `claude-login` уже шарит.
- **Два экземпляра приложения работают одновременно** — проверено экспериментом: процесс с другим `CLAUDE_USER_DATA_DIR` поднялся рядом с уже открытым, первый не пострадал, single-instance-замка нет. Поэтому переключение аккаунта не требует закрывать предыдущее окно, и формулировки в UI должны быть про «оба открыты», а не про «переключение».
- **`CLAUDE_USER_DATA_DIR` переносит весь каталог данных:** `app.setPath("userData", <dir>)`, логи в `<dir>/Logs`.
- **Токен приложения зашифрован Electron safeStorage** (значения начинаются с `djEw…` — префикс `v10`), ключ в Keychain-элементе `Claude Safe Storage`. Мы его **не расшифровываем**: `app_status` смотрит только на наличие ключей. Подменять блоб не нужно — `CLAUDE_USER_DATA_DIR` решает задачу без криптографии.
- **Логин приложения отдельный от CLI.** Приложение — «хост» провайдера: сайдкару отдаются `CLAUDE_CODE_HOST_CREDS_FILE`, `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST=1`, `CLAUDE_CODE_HOST_AUTH_ENV_VAR`. Элемент `Claude Code-credentials` для сессий приложения не используется, `claude auth login` приложение не логинит.
- **В файле сессии есть всё для продолжения:** `cliSessionId`, `cwd`, `originCwd`, `title`/`titleSource`, `model`, `effort`, `permissionMode`, `isArchived`, таймстемпы. Префикс имени — `local_`.
- **`CLAUDE_SECURESTORAGE_CONFIG_DIR` отвязывает имя Keychain-элемента от `CLAUDE_CONFIG_DIR`:** если переменная задана, хеш считается от неё, а если задана пустой — суффикс не добавляется вовсе. `claude_cli.credentials_service` про неё не знает и при выставленной переменной посчитает не то имя. Это дырка, не связанная с приложением, — не забыть.
- Не использованное, но известное: IPC-метод `importCliSession(cliSessionId)` втягивает CLI-транскрипт в список текущего аккаунта (в логах есть «deep-link import race», то есть внешний триггер существует, но форма ссылки не выяснена); deep-link схемы `claude://` и `claude-cli://`; вариант сборки «3p» с `userData + "-3p"` и `configLibrary/<uuid>.json` — на основной путь не влияет.

Инварианты этой части:

1. **`config.json` не шарится никогда.** В нём токен аккаунта и `lastKnownAccountUuid` — ровно то, что делает профили разными. Он не входит в `claude_app.DEFAULT_APP_SHARED` и не должен туда попасть.
2. **Лист залогиненного аккаунта сворачивается копированием, а не перемещением.** Приложение пишет только в `<currentAccountId>/<currentOrgId>`, поэтому остальные листы того же каталога переносятся обычным `move`, а живой — через `_drain_live_into_pool`: копия → `rename` каталога в `<org>.replaced-<ms>` → симлинк → повторная досылка. Оригинал не удаляется никогда. Требовать закрыть окно, в котором человек работает, — плохой обмен за гонку короче миллисекунды, которая не может потерять данные. Кого считать живым, решает `commands.pool_guard`; если каталог открыт, а аккаунт не читается, не переносится ничего.
3. **Ссылка на пул ставится до запуска приложения, а не после.** Каталог `<acct>/<org>` приложение создаёт только после логина — когда `claude-login` уже завершился. Поэтому `link_session_pool` вызывается заранее, `orgUuid` берётся с диска (`known_org_uuids`) или из API и кешируется в реестр. Без этого первый запуск нового аккаунта показывает пустой список, и непонятно, когда он перестанет быть пустым.
4. **`CLAUDE_CONFIG_DIR` вычищается из окружения приложения** (`claude_app.child_env`). Иначе сайдкар уведёт транскрипты из общего `~/.claude/projects`, и продолжение чата между аккаунтами перестанет работать — то есть отвалится главная фича.
5. **Машинный каталог приложения — это профиль `default`**, аналог `~/.claude`: он источник общего, симлинки в него не ставятся, но его чаты в пул забираются. `commands.app_data_dirs` включает его всегда и не зависит от того, есть ли у `~/.claude` свой CLI-логин.
6. **Отсутствие списка аккаунтов значит «все», пустой список — «никто».** Это касается `appOpenAccounts` и `appSharedAccounts`; различие между отсутствием ключа и пустотой — единственное, что позволяет свежей установке вести себя очевидно, а пользователю всё же выбрать «никого». Читать только через `Vault._account_list`, не через `.get(...) or []`.
7. **Шаринг чатов — свойство аккаунта, применяемое к листу.** Лист называется `<accountUuid>/<orgUuid>`, поэтому фильтр `sharing` в `wire_session_pool` сравнивает `leaf.parent.name`, а не смотрит на каталог целиком: в машинном каталоге лежат листы разных аккаунтов, и невыбранный обязан остаться приватным даже там.
8. **Скрипты не содержат логики.** Любое правило, которое захочется положить в `.command`, — это подкоманда в `commands.py` с тестом. В shell его никто не проверит; `TestScripts` следит, чтобы обёртки не разрослись.
9. **Запуск приложения — `Popen(start_new_session=True)`, не `execve`.** GUI обязан переживать закрытие терминала. И не `open -a`: он не передаёт окружение, а окружением как раз и выбирается аккаунт.

Ловушки этой части:

- **`pgrep -f` не видит главный процесс приложения.** Проверено: он находит два десятка хелперов и пропускает тот, который важен. Поэтому `claude_app` разбирает вывод `ps -Ao pid=,command=`. Не «упрощать» обратно на `pgrep`.
- **Какой профиль открыт, видно только по хелперам.** У главного процесса в argv нет ничего полезного, а каждый хелпер несёт `--user-data-dir=<путь>` — отсюда `running_data_dirs()`. Значение содержит пробелы (`Application Support`), поэтому парсится регуляркой до следующего ` --`, а не `split()`.
- **`local-agent-mode-sessions` выглядит как второй индекс чатов, но это рабочий каталог.** Внутри листа лежат `cowork_plugins`, `backups`, `debug`, `rpm`, свой `.claude.json`, вложенные каталоги по accountUuid; а первый уровень не всегда accountUuid — там же живёт `skills-plugin`. Пулить его нельзя: это смешивает состояние, не имеющее отношения к истории чатов. `POOL_DIRNAMES` содержит **только** `claude-code-sessions`. Ошибка стоила данных: перенос двигал лишь файлы, а потом делал `rmtree` листа — вложенные каталоги удалялись. Теперь `wire_session_pool` никогда не удаляет то, чего не перенёс: остаток попадает в `PoolPlan.unmoved`, лист остаётся как есть. Регрессия закрыта `test_a_directory_inside_a_leaf_is_never_deleted`.
- **Два имени в `DEFAULT_APP_SHARED` содержат пробелы** — `Claude Extensions` и `Claude Extensions Settings`. Любая правка этого списка через строку с разделителем-пробелом рвёт их на `Claude`, `Extensions`, `Settings`; `link_app_shared` затем молча пропускает несуществующее (так и задумано для необязательных записей), и расширения перестают шариться **без единого сообщения об ошибке**. Ровно это и случилось на живой машине: в профиле накопилось 206 МБ своих расширений, которые пользователь переустановил руками. Поэтому экран правки — только список с галочками (`cmd_settings_shared`), никаких `split()`. Регрессия закрыта `TestSharedEntryEditing`.
- **`sync-all` обязан считать нерешённое расхождение неуспехом.** `cmd_app_relink` возвращает `1`, если чья-то приватная копия осталась, иначе кнопка печатала «everything that can be shared is shared» поверх непошаренных расширений. Из-за этого же `sync-all` зовёт `app relink` с `force=True`: разобрать приватную копию — это и есть его работа, копия сохраняется в `.shadowed`.
- **`<org>.replaced-<ms>` рядом с листом — наш бэкап, а не забытый каталог.** Он лежит там же, где симлинк, поэтому исключён из `claude_app.session_leaf_dirs` по `REPLACED_MARKER`. Забыли исключить — и `doctor` с `pending_pool_labels` вечно докладывают, что «есть непошаренный каталог».
- **Приложение держит индекс чатов в памяти.** Правки в пуле оно видит с задержкой (`LIST_MEMO_TTL_MS`, 30 с), а записи, уже загруженные в память, может записать обратно. Поэтому `sweep_pool` авторитетен только для данных, которые никто не держит открытым; бороться подметанием с работающим приложением бессмысленно.
- **Запись в индексе чатов может быть мертвее транскрипта.** Индекс приложения переживает `~/.claude/projects` — на живой машине из 83 чатов старого аккаунта не нашлось ни одного транскрипта, и в общем списке они умели только отвечать «session not found on disk». Поэтому `Vault.sweep_pool` уносит такие записи в `app-shared/orphans`, а `claude_cli.transcript_ids` строит индекс живых id одним проходом. Записи без `cliSessionId` — это несостоявшиеся сессии, их не трогаем.
- **Симлинк на каталог устойчивее, чем на файл.** Атомарная запись рвёт ссылку на файл, но не на каталог, — поэтому пул связывается на уровне каталога `<acct>/<org>`, а не по файлам.
- **`app relink` c именем профиля не трогает машинный каталог**, потому что фильтр по имени означает «только этот профиль». Пул машинного каталога подхватывается только в общем прогоне.

## Правила для агента

0. **Ничего личного в репозиторий.** Ни почт, ни UUID аккаунтов, ни путей `/Users/<имя>` — проект рассчитан на публикацию. `TestNoPrivateData` это проверяет; если он упал, чините данные, а не тест.
1. После любой правки прогнать `python3 -m unittest discover -s tests` и показать результат. «Должно работать» — не результат.
2. Новую логику покрывать тестом в `tests/test_claude_login.py`; тесты идут против заглушки `claude`, реальных аккаунтов не касаться.
3. Зависимости не добавлять. Ни одну.
4. Не коммитить и не пушить без явной просьбы. Каталог сейчас вообще не `git`-репозиторий — если понадобится история, спросить, прежде чем делать `git init`.
5. Правки — точечным редактированием, а не перезаписью файла целиком.
6. Ничего не печатать и не логировать из содержимого кредов, даже частично, даже в отладке.
7. Знание про раскладку Claude Code держать в `claude_cli.py`, про настольное приложение — в `claude_app.py`. Не размазывать по `commands.py`.
8. Записи в реестр — только внутри `vault.locked()`.
9. Не менять `~/.claude`, `~/.claude-accounts` и `~/Library/Application Support/Claude` пользователя в ходе разработки: тесты для этого и подменяют пути. Ручные эксперименты — через `CLAUDE_ACCOUNTS_HOME` и `CLAUDE_LOGIN_APP_SUPPORT` на временные каталоги.
10. Не удалять и не перезаписывать данные профиля, если непонятно, чьи они: существующий паттерн — уносить в `.shadowed/`, а не в `/dev/null`.
