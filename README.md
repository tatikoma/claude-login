# claude-login

Локальная утилита для переключения между несколькими аккаунтами Claude Code,
которые принадлежат вам и находятся под вашим контролем. Для каждого аккаунта
она держит отдельный профиль со своим логином и запускает настоящий `claude` —
или настольное приложение Claude — под тем аккаунтом, который вы выбрали.

Утилита не предназначена для того, чтобы делиться кредами или платным доступом
либо давать нескольким людям доступ к одному аккаунту Claude.

Запускаете `claude-login` — видите список своих аккаунтов со статусом логина и
расходом лимитов каждого, выбираете стрелками, жмёте Enter, и запускается
настоящий `claude` под этой учёткой. С какими флагами — настраивается в разделе
настроек (клавиша `s`); по умолчанию — без флагов.

```
Select a Claude Code account

      ACCOUNT       PLAN       5H                    WEEK                   STATUS
❯ work@example.com  max     4% ⟳ 17:10   96% ⟳ 28.07 23:00 · Fable 100%  ok
  me@home.com       pro   100% ⟳ 14:20   38% ⟳ 29.07 01:00               ok
  acme@corp.com     max      —             —                             not signed in

↑↓ move · ⏎ launch · a add · s settings · r reload · d delete · p prune · q quit
```

Колонки `5H` и `WEEK` — расход лимитов **этого** аккаунта в процентах и конец
окна, живьём из API (тот же эндпоинт, что за `/usage` внутри сессии). Это только
чтение: лимиты каждого аккаунта считаются отдельно, утилита их не суммирует и не
обходит, а аккаунт по ним не выбирает — выбираете вы.

## Назначение

`claude-login` рассчитан на аккаунты, которые принадлежат одному человеку и
находятся под его контролем. Типичные сценарии:

- выбрать, под каким из своих аккаунтов запустить Claude Code или приложение;
- видеть статус логина и расход лимитов каждого своего аккаунта в одном
  локальном списке;
- не настраивать заново под каждый аккаунт настройки, скиллы, плагины и
  MCP-серверы;
- продолжить локальную работу под другим своим аккаунтом — с последствиями,
  описанными в разделе [Общая история диалогов](#общая-история-диалогов).

Утилита не предназначена для того, чтобы:

- давать доступ к аккаунту другим людям;
- делиться сессиями авторизации;
- перепродавать или раздавать доступ;
- обходить ограничения аккаунта или меры, которыми сервис их обеспечивает.

Это описание назначения, а не техническая гарантия: проверить, чей аккаунт в неё
добавили, утилита не может.

## Рамки

`claude-login` — локальная утилита для одного пользователя: всё работает на
одной машине под одним пользователем ОС. Своего сервера, удалённой
синхронизации, командного доступа и раздачи кредов между людьми в проекте нет.

Каждый добавленный аккаунт должен:

- принадлежать вам;
- использоваться по условиям, которые действуют для этого аккаунта;
- быть залогинен отдельно — собственным входом через `claude auth login` или в
  самом приложении.

Где лежат креды и что уходит в сеть — в разделе
[Креды и безопасность](#креды-и-безопасность).

## Первый запуск

```bash
./install.sh                 # симлинки claude-login и ccl в ~/.local/bin
claude-login setup           # проведёт по шагам: аккаунты, режим запуска, общее
```

`setup` спрашивает только то, что нельзя решить за вас, и его можно запускать
повторно сколько угодно — он ничего не ломает и лишнего не создаёт. В конце он
без отдельного вопроса запускает `sync-all`, то есть включает общую историю
диалогов и общий список чатов приложения для всех аккаунтов — что это значит,
описано в разделе [Общая история диалогов](#общая-история-диалогов). Дальше
достаточно набрать `claude-login`.

Если командная строка не ваш инструмент, всё то же самое лежит в `scripts/` и
запускается двойным кликом из Finder — см. [Скрипты](#скрипты).

Нужен Python 3.9+, установленный `claude` и, для работы с приложением, macOS.
Зависимостей у самой утилиты нет ни одной.

**Никаких кредов вставлять в проект не нужно.** Логинит вас настоящий
`claude auth login` и само приложение, они же хранят токены — в Keychain и в
своих каталогах. `claude-login` только показывает им другой каталог, поэтому в
репозитории нет и не может быть ни ключей, ни почт, ни идентификаторов
аккаунтов; всё личное живёт в `~/.claude-accounts` за пределами проекта. На
это есть тест-сторож, который валит сборку, если что-то подобное туда попадёт.

## Скрипты

Пять файлов в `scripts/`, каждый — двойной клик в Finder:

| файл | что делает |
| --- | --- |
| `setup.command` | первый запуск: проверки, аккаунты, общее |
| `add-account.command` | залогинить новый аккаунт и открыть под ним чистое окно |
| `open-accounts.command` | открыть приложение под каждым выбранным аккаунтом |
| `sync-all.command` | раздать скиллы, MCP-серверы и чаты между аккаунтами |
| `doctor.command` | показать, что связано, а что нет |

Логики внутри нет — это обёртки над командами, чтобы не держать в голове,
какую из них когда звать. Окно после выполнения не закрывается, чтобы можно
было прочитать вывод.

Два замечания для того, кто получил проект архивом:

- запустите `./install.sh` — в zip теряется бит исполняемости, и двойной клик
  молча не сработает;
- первый запуск `.command` из скачанного архива macOS блокирует карантином:
  правый клик → «Открыть» → «Открыть». Дальше кликается обычно.

## Как это работает

Claude Code берёт и конфиг, и креды из `CLAUDE_CONFIG_DIR`:

| что | без переменной | с `CLAUDE_CONFIG_DIR=<dir>` |
| --- | --- | --- |
| конфиг | `~/.claude.json` | `<dir>/.claude.json` |
| Keychain | `Claude Code-credentials` | `Claude Code-credentials-<sha256(dir)[:8]>` |
| fallback-файл | `~/.claude/.credentials.json` | `<dir>/.credentials.json` |

Поэтому каждому аккаунту достаётся собственный каталог в
`~/.claude-accounts/profiles/<name>`, и логины физически не пересекаются:
токены живут в отдельных элементах Keychain, `claude auth login` одного профиля
не выкидывает остальные, а два аккаунта спокойно работают одновременно в разных
окнах терминала.

Глобальный `~/.claude` при этом не трогается вообще: он остаётся профилем
`default` в списке и помечен там `(default)`: под `~/.claude` может быть
залогинен тот же аккаунт, что и у отдельного профиля, и без пометки эти две
строки не различить.

### Как выбирается аккаунт

Только вручную: стрелками в списке или по имени (`claude-login work`). Курсор в
списке стоит на последнем использованном аккаунте. Сама утилита аккаунт не
выбирает и не меняет: по расходу лимитов не сортирует, при исчерпании лимита не
переключает.

Выбор действует на новый запуск: утилита замещает себя процессом `claude`
(`execve`) с `CLAUDE_CONFIG_DIR` выбранного профиля, а уже запущенная сессия
остаётся под своим аккаунтом. Несколько аккаунтов могут работать одновременно,
каждый в своём окне. У приложения — своё окно на аккаунт; `claude-login app
open` открывает их разом для аккаунтов из списка `Accounts to open`, а пока
список не настраивали — для всех.

### Что остаётся общим

Чтобы не заводить настройки, память и историю заново на каждый аккаунт, в каталог
профиля при `add` кладутся симлинки на `~/.claude`. Список-кандидат:

`settings.json`, `CLAUDE.md`, `commands`, `agents`, `skills`, `workflows`,
`output-styles`, `rules`, `hooks`, `plugins`, `projects`, `file-history`,
`history.jsonl`

Ссылка появляется только на то, что в `~/.claude` действительно есть: на
типичной машине половины списка нет, и пустые каталоги ради неё не создаются.

Три записи из списка — история: `projects` (транскрипты диалогов),
`file-history` (парные к ним чекпойнты для `/rewind`, они ходят вместе) и
`history.jsonl` (история введённых промптов). Что из этого следует — в разделе
[Общая история диалогов](#общая-история-диалогов).

Личным у профиля остаётся только то, что действительно привязано к учётке:
креды в Keychain, `oauthAccount`, кеши лимитов и телеметрия — плюс
`sessions/` (это не история диалогов, а `<PID>.json` живых процессов) и
`shell-snapshots`, `session-env`, `tasks`, `jobs`, которые машинно-локальные и
пересоздаются сами.

Список хранится в `~/.claude-accounts/accounts.json` (ключ `shared`) и один на
все профили. `claude-login relink` досоздаёт ссылки на добавленные в него записи,
но ссылку на убранную запись в существующих профилях не трогает — её удаляют
руками (`rm` на симлинке убирает саму ссылку, а не общий файл).

### Почему симлинк, а не хардлинк

Claude Code пишет конфиги атомарно — во временный файл рядом и `rename`. Само по
себе это симлинки рвёт (`mv tmp link` заменяет ссылку обычным файлом), но
Claude Code **резолвит путь до реального файла перед записью**, поэтому `rename`
приземляется на цель ссылки, а не на неё саму.

Проверено на настоящем бинарнике: `claude auto-mode reset` (пишет `settings.json`)
и `claude mcp add` (пишет `.claude.json`), запущенные внутри профиля:

| | симлинк | хардлинк |
| --- | --- | --- |
| ссылка после записи | **цела** | **разорвана** (у профиля новый inode) |
| изменение видно в `~/.claude` | да | нет, общий файл остался старым |
| inode общего файла | сменился — писали именно в него | не менялся |

То есть симлинк работает ровно как задумано, а хардлинк разъехался бы на первой
же правке настроек из профиля. Плюс каталоги хардлинком не связать в принципе
(`ln: Is a directory`), а в общем списке каталогов большинство.

Тест-канарейка на это поведение лежит в `tests/` — если будущая версия Claude
Code перестанет резолвить путь, он это поймает.

Страховка на всякий случай всё равно есть: если ссылка когда-нибудь всё же
превратится в отдельный файл (сторонний редактор, ручной `cp`, смена поведения),
`claude-login doctor` покажет это как `diverged`, `claude-login relink` вернёт
ссылку молча, если копия побайтово совпадает с общей, а `relink --force` уберёт
разошедшуюся копию в `<профиль>/.shadowed/`. Без `--force` чужие данные не
трогаются.

### `.claude.json` — единственное, что не шарится напрямую

В нём лежат и общие вещи (доверенные папки, `mcpServers`, состояние онбординга),
и сам аккаунт (`oauthAccount`) — поэтому симлинком его сделать нельзя. При
создании профиля общая половина **копируется** (отключается флагом `--no-seed`),
а дальше подтягивается по требованию:

```bash
claude-login sync          # для всех профилей
claude-login sync work     # для одного
```

`sync` перезаписывает `mcpServers`, `theme`, флаги онбординга из основного
`~/.claude.json`, а `projects` **сливает**: профиль получает новые доверенные
папки, но своя пер-проектная история промптов не затирается. `oauthAccount` не
трогается никогда.

**Личным для каждого профиля остаётся:** сами креды, `oauthAccount`, сессии,
телеметрия и кеши — то есть ровно то, что привязано к аккаунту.

## Общая история диалогов

Утилита работает только с локальными файлами истории самого Claude Code: никуда
их не отправляет и своей копии не держит. Общей между аккаунтами история
становится потому, что все профили смотрят в одни и те же файлы. **По умолчанию
это включено для всех аккаунтов.**

**CLI.** `projects`, `file-history` и `history.jsonl` — симлинки на
`~/.claude` (см. [Что остаётся общим](#что-остаётся-общим)), поэтому
`--continue`, `--resume` и `/resume` под любым аккаунтом видят диалоги,
начатые под остальными, а история промптов у всех одна. Список общих записей
один на все профили: выключить историю у одного аккаунта, оставив её у других,
нельзя.

**Приложение.** Каталог данных у каждого аккаунта свой, но каталог его чатов
вкладки Code — симлинк на общий пул, где у каждой организации свой подкаталог.
Поэтому список Recents одинаков у всех аккаунтов одной организации, а у аккаунтов
разных организаций остаётся разным (подробности — в разделе
[Claude Code App](#claude-code-app)). Сами транскрипты чатов приложения лежат в
общем `~/.claude/projects` при любых настройках: утилита запускает приложение без
`CLAUDE_CONFIG_DIR`, как это было бы и без неё, — и через CLI (`--resume`) они
видны каждому профилю, у которого общий `projects`, из какой бы организации ни
был аккаунт.

**Что происходит при продолжении под другим аккаунтом.** Начали диалог под
аккаунтом A, продолжили под аккаунтом B — следующие запросы уходят в API
Anthropic под аккаунтом B и несут с собой контекст диалога, в том числе всё, что
было написано под A. Обрабатываются они по условиям и настройкам данных аккаунта
B. Если это неприемлемо — например, у ваших аккаунтов разные правила обращения
с данными, — общую историю стоит выключить.

**Как выключить.**

- CLI: убрать `projects`, `file-history` и `history.jsonl` из ключа `shared` в
  `~/.claude-accounts/accounts.json` и удалить эти симлинки в каталогах
  профилей — сам `relink` убранные записи не снимает. Профиль начнёт свою
  историю с нуля, а общая останется в `~/.claude`, то есть у профиля `default`.
- Приложение: `Settings → Claude Code App → Accounts sharing chats`, снять
  галочку с аккаунта. Сейчас эту настройку соблюдает только запуск приложения
  через утилиту, а `sync-all`, `setup`, `app adopt`, `app relink` и `app link`
  возвращают аккаунт в пул — подробности в разделе
  [Claude Code App](#claude-code-app). Транскрипты при этом остаются в общем
  `~/.claude/projects`.

## Команды

```
claude-login                      список профилей, выбор стрелками, запуск claude
claude-login work                 сразу запустить claude под профилем work
claude-login work --resume        любые лишние аргументы уходят в claude
claude-login -- --model opus      то же, но профиль выбирается в списке

claude-login add                  залогинить новый аккаунт (имя возьмётся из email)
claude-login list                 таблица с лимитами и статусом токенов
claude-login list --no-usage      без похода в сеть
claude-login list --json          то же машиночитаемо
claude-login rename a@b.com job   переименовать профиль
claude-login remove a@b.com       удалить профиль, перед этим claude auth logout
claude-login prune                убрать протухшие/битые профили
claude-login prune --dry-run      только показать, что удалилось бы
claude-login prune --stale-days 30  плюс те, которыми не пользовались 30 дней
claude-login setup                первый запуск: проверки, аккаунты, общее
claude-login sync-all             раздать скиллы, MCP и чаты между аккаунтами
claude-login work --app           запустить приложение Claude под профилем work
claude-login app open             открыть приложение под всеми выбранными аккаунтами
claude-login app                  состояние профилей приложения
claude-login app adopt            собрать существующие чаты приложения в общий пул
claude-login app relink           пересоздать общие ссылки приложения
claude-login settings             раздел настроек: цель запуска, флаги, App (или `s`)
claude-login flags                показать флаги запуска claude
claude-login flags -- --continue  заменить их
claude-login flags --clear        запускать claude без флагов
claude-login env work             напечатать export CLAUDE_CONFIG_DIR=...
claude-login relink               пересоздать общие симлинки
claude-login relink --force       плюс убрать разъехавшиеся копии в .shadowed/
claude-login sync                 подтянуть доверенные папки и MCP из ~/.claude.json
claude-login sync --gather        сначала собрать MCP, добавленные внутри профилей
claude-login doctor               диагностика
```

Алиасы: `ls`→`list`, `rm`/`delete`→`remove`, `clean`→`prune`, `run`/`switch`→`use`,
`new`/`login`→`add`. Имя можно сокращать: `claude-login work` найдёт
`work@example.com`.

### Никаких имён и подписей

`claude-login add` ничего не спрашивает: открывает браузер, а после логина сам
берёт email из аккаунта и называет профиль по нему. Логин при этом идёт во
временный каталог — итоговое имя известно только после него, — а потом каталог
переезжает вместе со своим элементом Keychain. Прерванный логин не оставляет
ни профиля, ни мусора; повторно добавить уже заведённый аккаунт нельзя.

Если очень нужно другое имя каталога — `claude-login add короткое-имя`.

Остальные опции `add`: `--console` (аккаунт Anthropic Console), `--sso`
(принудительно вход через SSO) и `--email` (подставить почту на странице входа)
уходят в `claude auth login`; `--no-seed` не копирует общую половину
`~/.claude.json`, а `--use` и `--no-use` сразу запускают новый аккаунт или даже
не предлагают этого.

### Лимиты

Колонки `5H` и `WEEK` берутся из `GET /api/oauth/usage` — того же эндпоинта,
что показывает `/usage` внутри сессии. Значения всегда живые: ничего не
кешируется между запусками, потому что лимит, показывающий `4%`, когда он на
самом деле выбран, хуже отсутствия цифры. Не получилось запросить — будет `—`.

Интерактивный список сеть не ждёт: он рисуется сразу (~100 мс) с
многоточием `…` в колонках лимитов, а цифры подставляются, когда придут
(~0.3–0.7 с). `claude-login list` печатается один раз и потому ждёт ответа (до
6 с). Клавиша `r` перезапрашивает, `--no-usage` не запрашивает лимиты вовсе.

Конец окна показывается всегда, а не только когда упёрлись в лимит:
`4% ⟳ 17:10`, `96% ⟳ 28.07 23:00`. У пятичасового окна выводится одно время,
если оно закрывается сегодня, и время с датой, если уже завтра.

Цвет: до 60% зелёный, до 85% жёлтый, дальше красный, на 100% — красный жирный.
Само время приглушено, чтобы первым читался процент; на 100% оно подсвечивается
вместе с ним, потому что там важно именно оно.

Если выбран **недельный** лимит, пятичасовой красится красным независимо от
своего значения: пустое пятичасовое окно ни на что не годится, пока недельное
исчерпано, и зелёные `0%` вводили бы в заблуждение.

`0% ⟳ —` значит, что пятичасовое окно ещё не открыто: оно стартует с первого
запроса, и до этого конца у него нет — API отдаёт `resets_at: null`.

`WEEK` — это общий недельный лимит. Если отдельный лимит на модель (Opus, Fable)
уже выбран, а общий ещё нет, он дописывается рядом:
`96% ⟳ 28.07 23:00 · Fable 100%` — иначе аккаунт выглядел бы рабочим, хотя нужная
модель уже недоступна. Время у него печатается, только если отличается от общего.

Если у аккаунта протух access-токен (живёт ~8 часов), он обновляется через
`POST /v1/oauth/token` — ровно как это делает сам Claude Code, — и новые токены
записываются обратно в хранилище профиля. Обновление происходит **только** когда
токен реально истёк: валидный используется как есть, чтобы не устроить гонку с
работающей сессией. Касается это каждого аккаунта в списке, а не только того,
который вы потом запустите, — поэтому аккаунт, которым давно не пользовались,
но который виден в списке, остаётся залогиненным.

Запросы ко всем аккаунтам идут параллельно, в потоках. Asyncio тут ничего не
даёт — замер показал, что запросы и так шли внахлёст, а лишнее время съедал
`urllib.request`, который на каждый вызов собирает цепочку обработчиков.
Переход на `http.client` дал 410 → 275 мс на трёх аккаунтах; asyncio на сырых
сокетах — 294 мс, то есть неотличимо от потоков.

HTTP/3 недоступен: `api.anthropic.com` не отдаёт заголовок `alt-svc`, то есть
QUIC не анонсирует вообще, а ALPN согласует `h2` поверх TLS 1.3. Да он бы и не
помог — в разбивке одного запроса (DNS 2 мс, TCP 80 мс, TLS 78 мс, **TTFB
436 мс**, тело 0 мс) сэкономить можно было бы только TLS-рукопожатие, ~13% от
общего времени. Мультиплексирование HTTP/2 тоже не дало бы ничего по
времени: три рукопожатия и так идут одновременно, в трёх потоках. 73% времени —
это ответ `api.anthropic.com`, и на него ускорение клиента не влияет никак.

### Аргументы запуска

В коде дефолтов нет вообще: свежее хранилище запускает `claude` без флагов.
Всё лежит в конфиге, в ключе `launchArgs` (`~/.claude-accounts/accounts.json`).

Настраивается в интерфейсе — клавиша `s` в списке аккаунтов или
`claude-login settings`:

```
Settings — launch flags

claude --dangerously-skip-permissions --continue --effort max

           SETTING                         FLAG               VALUE
❯ Skip permission prompts     --dangerously-skip-permissions  on
  Continue last conversation  --continue                      on
  Reasoning effort            --effort                        max
  Other flags                 —                               edit

↑↓ move · ⏎ change · e edit as text · c clear all · q back
```

Enter переключает строку (у `--effort` перебирает `off → low → … → max`),
верхняя строка сразу показывает получившуюся команду. `Other flags` — всё
остальное, что не разложено на переключатели.

То же из командной строки:

```bash
claude-login flags                                       # показать текущие
claude-login flags -- --effort max --continue            # заменить
claude-login flags --clear                               # запускать голый claude
claude-login --no-flags work                             # разово без флагов
```

Аргументы складываются в три слоя: `launchArgs` → `extraArgs` профиля →
то, что вы набрали после имени аккаунта. Правый слой перебивает левый по имени
флага, так что `claude-login work --effort low` победит `--effort max` из
конфига, а дубля не будет. `-c` и `-r` считаются теми же флагами, что
`--continue` и `--resume`.

Флаги самого `claude-login` (`--no-flags`, `--no-usage`, `-r`) идут **до** имени
аккаунта, всё что **после** — уходит в `claude` как есть.

Постоянные аргументы для конкретного аккаунта — в его `extraArgs` там же,
например `"extraArgs": ["--model", "opus"]`.

### Автопродолжение последнего диалога

`--continue` в `launchArgs` продолжает последний диалог в текущем каталоге.

Ставить его безусловно нельзя: без транскрипта `claude --continue` не начинает
новую сессию, а **прерывает запуск** с `No conversation found to continue`
(проверено по коду и на живом бинарнике). Поэтому перед запуском проверяется,
есть ли непустой транскрипт для текущего каталога, — и если нет, флаг просто не
передаётся. Каталог вычисляется по тому же правилу, что и у Claude Code:
все не-алфанумерики в пути меняются на `-`, а путь длиннее 200 символов
обрезается и получает хвост-хеш.

`--continue` также снимается, если вы явно передали `--resume` — они конфликтуют.

Транскрипты (`projects/`) общие между аккаунтами, так что диалог продолжится
независимо от того, под какой учёткой вы его начинали, — а запросы пойдут уже
под текущей. Что это значит для данных — в разделе
[Общая история диалогов](#общая-история-диалогов).

## Claude Code App

То же самое для настольного приложения. Раньше смена аккаунта в приложении
означала логаут, логин — и пустой список проектов и чатов: приложение хранит
индекс сессий вкладки Code по пути

```
<каталог данных>/claude-code-sessions/<accountUuid>/<orgUuid>/<id>.json
```

то есть под **текущим** аккаунтом. Вошли под другим — приложение смотрит в другой
каталог и не находит ничего. Сами диалоги при этом никуда не девались: в каждом
файле сессии есть `cliSessionId`, а транскрипт лежит в общем
`~/.claude/projects` — том же, что у CLI.

`claude-login` решает это двумя приёмами:

- **каталог данных на аккаунт.** Приложение читает `CLAUDE_USER_DATA_DIR` ровно
  так, как `claude` читает `CLAUDE_CONFIG_DIR`, поэтому каждому профилю достаётся
  свой `profiles/<имя>/app-data`. Логаут не нужен: аккаунты остаются
  залогиненными, и их окна **работают одновременно** — как терминалы в CLI;
- **общий пул чатов.** Каталог `<accountUuid>` в каждом профиле — симлинк на
  общий пул `app-shared/ccd-sessions`, внутри которого лежит по каталогу на
  организацию. Список Recents получается одинаковым у всех аккаунтов одной
  организации, и чат, начатый под одним из них, можно продолжить под другим — с
  последствиями, описанными в разделе
  [Общая история диалогов](#общая-история-диалогов).

  Ссылка стоит именно на уровне аккаунта: с версии 1.25927 приложение открывает
  свой каталог сессий с `O_DIRECTORY|O_NOFOLLOW` и симлинк в последнем
  компоненте пути не принимает — в macOS это `ENOTDIR`, и каждое сохранение
  чата молча падает. По той же причине аккаунты **разных организаций** слить
  нельзя: последний компонент пути создаёт приложение, а хардлинков на каталоги
  в APFS нет.

Общим становится **только индекс чатов вкладки Code**. Соседний
`local-agent-mode-sessions` намеренно не трогается: несмотря на похожее имя, это
не индекс, а рабочий каталог agent-mode — с плагинами Cowork, бэкапами и своим
`.claude.json`, — и объединять его между аккаунтами значило бы смешивать
состояние, не имеющее отношения к истории чатов.

```bash
claude-login work --app          запустить приложение под аккаунтом work
claude-login work --cli          принудительно CLI
claude-login app                 состояние: логин приложения и каталог по аккаунтам
claude-login app adopt           втянуть уже существующие чаты в общий пул
claude-login app adopt --dry-run только показать, что переедет
claude-login app link            связать аккаунт с пулом, не запуская приложение
claude-login app relink          пересоздать общие ссылки приложения
claude-login app relink --force  плюс убрать разъехавшиеся копии в .shadowed/
```

Цель запуска по умолчанию настраивается в `claude-login settings` — `CLI`, `App`
или `ask`. В списке аккаунтов `⏎` запускает цель по умолчанию, а `o` — другую,
так что заходить в настройки ради разового запуска не нужно. `--app` и `--cli`
работают и после имени аккаунта (это единственные флаги, которые не уходят в
`claude` как passthrough — у него их всё равно нет; если когда-нибудь появятся,
`claude-login work -- --app` их прокинет).

**Что общее, а что нет.** Общими становятся пул чатов, скачанный сайдкар-CLI и
VM-бандлы (иначе каждый аккаунт качал бы свои 250 МБ+), расширения и их
MCP-настройки: `claude-code`, `claude-code-vm`, `vm_bundles`,
`Claude Extensions`, `Claude Extensions Settings`,
`extensions-installations.json`, `claude_desktop_config.json`,
`git-worktrees.json`. Список лежит в `accounts.json` под ключом `appShared`.

`config.json` не шарится никогда: в нём токен аккаунта (зашифрованный Electron
safeStorage) и `lastKnownAccountUuid`. Именно он и делает профили разными.
Кеши, `Cookies`, `Local State` и прочее машинно-локальное тоже остаются личными.

**Сборки приложения новее ~1.34 удаляют `CLAUDE_USER_DATA_DIR` при старте**
(без подписанного Anthropic токена переменная не работает). Поэтому `claude-login`
называет каталог ещё и ключом Chromium `--user-data-dir`, который приложение
отбросить не может, — окна под отдельными аккаунтами продолжают работать.
Известная цена одна: в таком окне выключено спаривание с расширением Claude in
Chrome. Машинное окно (`default`) запускается без ключа, ровно как двойным кликом
из Finder. Если какая-то сборка начнёт запрещать этот ключ, `claude-login`
откажется открывать окно отдельного аккаунта — иначе вместо него открылось бы
машинное окно под тем, кто в нём залогинен; `doctor` показывает это отдельной
строкой.

**Логин в приложении отдельный от CLI.** Приложение само выступает провайдером
кредов для своего сайдкара (`CLAUDE_CODE_HOST_CREDS_FILE`,
`CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`), поэтому `claude auth login` его не
логинит: при первом запуске нового профиля приложение один раз попросит войти.
`claude-login app` показывает, где логин уже есть, а `doctor` предупредит, если в
каталоге профиля залогинен не тот аккаунт. Запускать такой каталог `claude-login`
по умолчанию отказывается — окно открылось бы под чужим аккаунтом; интерактивно
можно ответить «открыть всё равно», скриптам — `claude-login use --yes <name>
--app`, а текст ошибки подсказывает профиль, который открывает нужный аккаунт.

**Существующие чаты.** `claude-login app adopt` собирает всё, что уже есть, в
общий пул — включая машинный каталог приложения, который остаётся профилем
`default` (как `~/.claude` для CLI). Перед переносом копия каталогов сессий
кладётся в `app-shared/.backup-<ms>`; команды отката нет — вернуть прежнее
можно руками из этой копии.

**Закрывать приложение для этого не нужно.** Приложение пишет только в лист того
аккаунта, под которым залогинено (`lastKnownAccountUuid`), а какие каталоги
открыты, видно по `--user-data-dir` у его процессов. Поэтому:

- чаты остальных аккаунтов того же каталога просто переезжают — их никто не
  пишет;
- лист активного аккаунта не переносится, а сворачивается аккуратно: сначала
  копия в пул, затем подмена каталога симлинком (две системные вызова, гонка
  меньше миллисекунды), затем повторная досылка того, что могло записаться в
  промежутке. Оригинал остаётся рядом как `<accountUuid>.replaced-<ms>` и не
  удаляется, так что потерять запись нельзя даже теоретически.

Если каталог открыт, а прочитать залогиненный аккаунт не удалось, не переносится
ничего: угадывать тут нечего — тогда закройте окно и повторите.

**Чаты без транскрипта в пул не попадают.** Индекс чатов приложения живёт дольше,
чем сами транскрипты: запись может пережить свой файл в `~/.claude/projects` на
машины и месяцы — например, если каталог приложения переехал со старого
компьютера. В общем списке такая запись умеет только сказать «session not found
on disk», поэтому `adopt` уносит её в `app-shared/orphans`: данные сохраняются,
но список остаётся рабочим.

**Новый аккаунт.** Ссылку на пул `claude-login` ставит **до** запуска приложения,
и для этого достаточно `accountUuid` из реестра — каталог организации внутри пула
создаёт само приложение. Иначе получалось бы, что приложение создаёт свой каталог
сессий только после логина — то есть уже после того, как утилита завершилась, — и
первый запуск нового аккаунта показывал бы пустой список. `claude-login app link`
делает то же самое отдельно, без запуска приложения.

**Какие аккаунты участвуют — выбирается в настройках.** В разделе
`Settings → Claude Code App` две строки со списками и галочками:

- `Accounts to open` — кого открывает `app open` и скрипт;
- `Accounts sharing chats` — между кем общий список чатов. Если окно аккаунта
  закрыто, снятая галочка сразу отвязывает его от пула: он получает собственную
  копию — копию всего пула на этот момент, включая чаты других аккаунтов, — и
  дальше его новые чаты в общий список не попадают. Если окно было открыто,
  ссылка на пул остаётся: закройте окно, поставьте галочку и снимите её снова.
  Снять все галочки — то же, что выключить шаринг.

Пока в списки не заходили, они означают «все аккаунты»: на свежей установке
список чатов общий для всех.

**Оговорка: сейчас `Accounts sharing chats` соблюдает только запуск приложения
через утилиту.** `app relink` и `app link` смотрят лишь на то, включён ли шаринг
вообще, и связывают с пулом все аккаунты; `app adopt` сворачивает в пул чаты
всех аккаунтов, даже когда шаринг выключен целиком. `sync-all` и `setup`
вызывают эти команды, поэтому после них аккаунт со снятой галочкой снова
смотрит в общий пул.

**Расширения и их настройки — общие.** Всё, что стоит в приложении из каталога
расширений (`Claude Extensions`), симлинкуется в каждый профиль, поэтому
устанавливать их заново под другим аккаунтом не нужно. Если по какой-то причине
профиль обзавёлся своей копией, `claude-login sync-all` её разберёт и вернёт
ссылку, а копию положит в `<профиль>/app-data/.shadowed/` — оттуда её можно
удалить руками, когда убедитесь, что всё работает. `doctor` показывает такие
расхождения словом `diverged`.

**Что перенести нельзя.** Удалённые коннекторы — Google Drive и прочие, которые
подключаются в claude.ai, — привязаны к аккаунту на стороне Anthropic. Локально
у них лежат только идентификатор и список инструментов, а сама авторизация
живёт на сервере, поэтому скопировать их между аккаунтами невозможно: в каждом
подключаются отдельно. Скиллы, плагины, агенты, команды, хуки, `settings.json`,
`CLAUDE.md`, расширения приложения и его MCP при этом общие, а MCP-серверы CLI
раздаёт `claude-login sync-all`.

**Флагов запуска у приложения нет.** Модель, `effort` и режим разрешений живут не
в командной строке, а в файле каждой сессии, и приложение помнит последний выбор.
Раз каталог данных теперь свой на аккаунт, эти настройки автоматически стали
раздельными. Если запуску нужно передать что-то ещё, в настройках App есть
`Launch env` — список переменных окружения.

## Очистка неактуальных

`claude-login prune` разбирает четыре случая:

| статус | что это | что делает prune |
| --- | --- | --- |
| `expired` | refresh-токен протух (обычно ~11 дней простоя) | удаляет профиль и его Keychain-элемент |
| `logged-out` | каталог есть, логина нет — обычно прерванный `add` | удаляет |
| `missing` | каталог удалён руками | вычищает запись из реестра |
| orphan | каталог в `profiles/` без записи в реестре | удаляет каталог и элемент Keychain |

Без `--yes` всегда сначала показывает список и спрашивает подтверждение.
Профиль `default` (то есть `~/.claude`) prune не трогает никогда.

Токен продлевается сам при запуске `claude`, поэтому чтобы аккаунт не протух,
достаточно иногда им пользоваться. `claude-login list` заранее подсвечивает
`expires in 2d` для тех, что скоро отвалятся.

## Диагностика

```bash
claude-login doctor
```

Показывает путь к `claude`, доступность Keychain, имя Keychain-элемента для
каждого профиля, сроки жизни токенов, незалинкованные общие файлы и запущенные
процессы `claude`.

## Где что лежит

```
~/.claude-accounts/
├── accounts.json           реестр + launchArgs + настройки App (0600, без секретов)
├── .registry.lock          блокировка на время записи реестра
├── .login/                 временные каталоги логина (чистятся сами)
├── app-shared/
│   ├── ccd-sessions/       общий пул чатов вкладки Code
│   │   └── <orgUuid>/      каталог на организацию — то, что открывает приложение
│   ├── orphans/            чаты, у которых не осталось транскрипта
│   ├── .backup-<ms>/       копия каталогов сессий перед первым переносом
│   └── collisions/         чаты, проигравшие спор за одинаковое имя
└── profiles/
    ├── work@example.com/   CLAUDE_CONFIG_DIR этого аккаунта
    │   ├── .claude.json    свой oauthAccount
    │   ├── settings.json -> ~/.claude/settings.json
    │   ├── projects      -> ~/.claude/projects
    │   └── app-data/       CLAUDE_USER_DATA_DIR приложения
    │       ├── config.json                свой токен приложения
    │       ├── claude-code -> общий сайдкар-CLI
    │       └── claude-code-sessions/<accountUuid> -> app-shared/ccd-sessions
    └── me@home.com/
```

Токены в файлах реестра не хранятся: на macOS они лежат в Keychain (пишет и читает
их сам Claude Code), на других системах — в `<профиль>/.credentials.json` с правами
`0600`, как это делает Claude Code.

Переменные окружения:

| переменная | зачем |
| --- | --- |
| `CLAUDE_ACCOUNTS_HOME` | другой корень хранилища (по умолчанию `~/.claude-accounts`) |
| `CLAUDE_LOGIN_CLAUDE_BIN` | другой бинарь `claude` |
| `CLAUDE_LOGIN_APP_PATH` | другой бандл приложения (по умолчанию `/Applications/Claude.app`) |
| `CLAUDE_LOGIN_APP_SUPPORT` | другой машинный каталог данных приложения |
| `CLAUDE_LOGIN_API_BASE` | другой хост API (по умолчанию `https://api.anthropic.com`) |
| `CLAUDE_LOGIN_OAUTH_CLIENT_ID` | другой OAuth client_id при обновлении токена |
| `CLAUDE_LOGIN_KEYCHAIN_PREFIX` | префикс имени элемента Keychain (`Claude Code`) |
| `CLAUDE_LOGIN_OAUTH_SUFFIX` | суффикс `OAUTH_FILE_SUFFIX` из сборки Claude Code |
| `HTTPS_PROXY` | прокси для запросов лимитов |
| `NO_COLOR` / `CLICOLOR_FORCE` | выключить / принудительно включить цвет |

`CLAUDE_LOGIN_KEYCHAIN_PREFIX` и `CLAUDE_LOGIN_OAUTH_SUFFIX` нужны, только если
Claude Code сменит схему именования элементов Keychain — тогда её можно
подкрутить, не трогая код.

## Креды и безопасность

Креды каждого аккаунта хранятся локально, на этой машине, и не предназначены для
передачи другим людям. Своего хранилища секретов, сервера и телеметрии у
`claude-login` нет: логинится настоящий `claude` (или приложение), он же пишет и
читает токены, а утилита показывает ему другой каталог.

**Где лежат креды.**

- CLI на macOS — элемент Keychain `Claude Code-credentials` у профиля `default`
  и `Claude Code-credentials-<sha256(каталог)[:8]>` у остальных; на других
  системах — `<профиль>/.credentials.json` с правами `0600`. Пишет их Claude Code.
- Приложение — `config.json` в каталоге данных профиля (`<профиль>/app-data`, у
  `default` — `~/Library/Application Support/Claude`), токен зашифрован Electron
  safeStorage. Утилита его не читает и не расшифровывает: проверяет только, есть
  ли нужный ключ.
- В `accounts.json` токенов нет вообще: там имена профилей, пути, `launchArgs`,
  настройки и карточка аккаунта, которую отдаёт API, — email, UUID, организация,
  тариф. Персональное, но не секретное; `0600` тут именно поэтому.

**Когда утилита сама трогает креды.** Читает — чтобы показать статус и
запросить лимиты. Переписывает — после обновления истёкшего access-токена и при
переносе каталога профиля (`add` логинится во временный каталог, `rename` меняет
путь), потому что имя элемента Keychain выводится из пути. Удаляет — в `prune` и
в `remove`, который перед этим зовёт `claude auth logout`, если не передан
`--keep-session`.

**Что уходит в сеть** — только запросы к `https://api.anthropic.com`:

| запрос | что несёт | когда |
| --- | --- | --- |
| `GET /api/oauth/usage` | access-токен профиля | `list` и интерактивный список, для каждого залогиненного аккаунта |
| `POST /v1/oauth/token` | refresh-токен и публичный `client_id` Claude Code | только когда access-токен истёк |
| `GET /api/oauth/profile` | access-токен профиля | только в `app link` (его же зовут `sync-all` и `setup`), если `orgUuid` аккаунта нет ни в реестре, ни на диске |

`CLAUDE_LOGIN_API_BASE` меняет хост — тогда токены уходят туда; через
`HTTPS_PROXY` к API прокладывается туннель, TLS при этом сквозной. `--no-usage`
отключает запросы лимитов, а с ними и обновление токенов ради них.

**Чего нет.** Команды экспорта или импорта кредов нет; `claude-login env`
печатает только `CLAUDE_CONFIG_DIR`. Идентификаторы, которые Claude Code держит в
каталоге профиля (в том числе для телеметрии), утилита не создаёт, не копирует
между профилями и не меняет.

**Что всё же переходит между профилями.** `sync` и `sync-all` копируют
`mcpServers` из `~/.claude.json` во все профили, а `sync --gather` (его зовёт
`sync-all`) сначала собирает туда серверы, добавленные внутри профилей. Если в
описании MCP-сервера есть ключ или токен — например, в его `env`, — он окажется
во всех профилях. То же касается общих `settings.json`, расширений приложения и
их настроек.

**Как обращаются с секретами там, где они проходят через код:**

- в `security(1)` секрет уходит **через stdin** (`security -i`), а не аргументом
  командной строки — иначе он был бы виден в `ps` любому процессу пользователя.
  Единственное исключение — блоб длиннее 4032 байт: `security -i` читает по
  команде на строку и такую строку уже не примет, тогда работает откат на argv.
  Это ровно то же поведение и тот же порог, что у самого Claude Code;
- `accounts.json` и `.credentials.json` создаются с правами `0600`, каталоги
  хранилища — `0700`;
- значения токенов не печатаются никуда и ни в каком виде: `list`, `doctor` и
  `--json` показывают только срок жизни и статус.

Само хранилище лежит в `~/.claude-accounts`, за пределами репозитория, так что
в коммит ничего личного не попадает. Это проверяется тестом `TestNoPrivateData`:
он проходит по файлам проекта и падает, если находит почту вне плейсхолдерных
доменов, UUID аккаунта или чей-то домашний каталог. Проект можно выкладывать
публично, не вычитывая его глазами каждый раз.

`client_id` в коде (`9d1c250a-…`) — не секрет: это публичный идентификатор
OAuth-клиента Claude Code, он зашит в сам бинарник и одинаков у всех.

## Тесты

```bash
python3 -m unittest discover -s tests            # изолированно, на заглушке claude
CLAUDE_LOGIN_INTEGRATION=1 python3 -m unittest discover -s tests   # + реальный Keychain
```

Интеграционные тесты — две канарейки на поведение настоящего Claude Code:
фиктивный токен кладётся в Keychain под вычисленным нами именем и проверяется,
что `claude auth status` его видит (формула имени элемента не разошлась); и что
запись `settings.json` не превращает симлинк в отдельный файл.

## Ограничения

- Переключение через Keychain — macOS. На Linux работает тот же механизм через
  `<профиль>/.credentials.json`.
- Общий `history.jsonl` дописывается всеми профилями сразу; если это мешает,
  уберите его из `shared` и удалите симлинк `history.jsonl` в каталогах
  профилей — `relink` убранную запись сам не снимает.
- Имя элемента Keychain утилита выводит только из `CLAUDE_CONFIG_DIR`. У
  актуального Claude Code его может перебить `CLAUDE_SECURESTORAGE_CONFIG_DIR`;
  если эта переменная задана, утилита будет искать креды не в том элементе.
- Выбор `Accounts sharing chats` пока соблюдает только запуск приложения через
  утилиту — см. оговорку в разделе [Claude Code App](#claude-code-app).
- Уже запущенная сессия `claude` продолжает работать под своим аккаунтом —
  переключение действует на новые запуски.
- Приложение — только macOS, и опирается на его внутреннюю раскладку
  (`CLAUDE_USER_DATA_DIR`, каталог сессий по `accountUuid`/`orgUuid`), которая
  недокументирована. Обновление приложения может её сменить; `claude-login
  doctor` показывает состояние ссылок и пула, `app relink` их восстанавливает.
- Приложение держит список чатов в памяти, поэтому изменения в пуле оно
  подхватывает не мгновенно (порядка десятков секунд) — и записи, которые уже
  были у него в памяти, может записать обратно. Свежий взгляд даёт перезапуск
  окна.
- При запуске из окружения убираются `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`
  и `CLAUDE_CODE_OAUTH_TOKEN` — иначе они перебили бы выбранный OAuth-аккаунт.
- `list` печатается один раз, поэтому ждёт сеть (6 с таймаут, параллельно);
  интерактивный список — нет, он рисуется сразу. `--no-usage` отключает
  обращение к сети полностью.
