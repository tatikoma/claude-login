# claude-login

Переключение между несколькими аккаунтами Claude Code из одного терминала.

Запускаете `claude-login` — видите список аккаунтов с текущим расходом лимитов,
выбираете стрелками, жмёте Enter, и запускается настоящий `claude` под нужной
учёткой. С какими флагами — настраивается в разделе настроек (клавиша `s`);
по умолчанию — без флагов.

```
Select a Claude Code account

      ACCOUNT       PLAN       5H                    WEEK                   STATUS
❯ work@example.com  max     4% ⟳ 17:10   96% ⟳ 28.07 23:00 · Fable 100%  ok
  me@home.com       pro   100% ⟳ 14:20   38% ⟳ 29.07 01:00               ok
  acme@corp.com     max      —             —                             not signed in

↑↓ move · ⏎ launch · a add · s settings · r reload · d delete · p prune · q quit
```

Колонки `5H` и `WEEK` — текущий расход лимитов в процентах и конец окна, живьём
из API (тот же эндпоинт, что за `/usage` внутри сессии).

## Установка

```bash
./install.sh          # симлинки claude-login и ccl в ~/.local/bin
./install.sh --pipx   # или изолированной pipx-программой
```

Зависимостей нет — только Python 3.9+ и уже установленный `claude`.

## Как это работает

Claude Code берёт и конфиг, и креды из `CLAUDE_CONFIG_DIR`:

| что | без переменной | с `CLAUDE_CONFIG_DIR=<dir>` |
| --- | --- | --- |
| конфиг | `~/.claude.json` | `<dir>/.claude.json` |
| Keychain | `Claude Code-credentials` | `Claude Code-credentials-<sha256(dir)[:8]>` |
| fallback-файл | `~/.claude/.credentials.json` | `<dir>/.credentials.json` |

Поэтому каждому аккаунту достаётся собственный каталог в
`~/.claude-accounts/profiles/<name>`, и логины физически не пересекаются:
токены живут в отдельных элементах Keychain, `claude auth login` одного профиля
не выкидывает остальные, а два аккаунта спокойно работают одновременно в разных
окнах терминала.

Глобальный `~/.claude` при этом не трогается вообще: он остаётся профилем
`default` в списке.

### Что остаётся общим

Чтобы не заводить настройки, память и историю заново на каждый аккаунт, в каталог
профиля кладутся симлинки на `~/.claude`:

`settings.json`, `CLAUDE.md`, `commands`, `agents`, `skills`, `workflows`,
`output-styles`, `rules`, `hooks`, `plugins`, `projects`, `file-history`,
`history.jsonl`

`projects` — это транскрипты диалогов, поэтому `--continue`, `--resume` и
`/resume` видят историю сквозь аккаунты; `file-history` — парные к ним чекпойнты
для `/rewind`, они ходят вместе.

Личным у профиля остаётся только то, что действительно привязано к учётке:
креды в Keychain, `oauthAccount`, кеши лимитов и телеметрия — плюс
`sessions/` (это не история диалогов, а `<PID>.json` живых процессов) и
`shell-snapshots`, `session-env`, `tasks`, `jobs`, которые машинно-локальные и
пересоздаются сами.

Список хранится в `~/.claude-accounts/accounts.json` (ключ `shared`) — можно
править и применять через `claude-login relink`.

### Почему симлинк, а не хардлинк

Claude Code пишет конфиги атомарно — во временный файл рядом и `rename`. Само по
себе это симлинки рвёт (`mv tmp link` заменяет ссылку обычным файлом), но
Claude Code **резолвит путь до реального файла перед записью**, поэтому `rename`
приземляется на цель ссылки, а не на неё саму.

Проверено на настоящем бинарнике: `claude auto-mode reset` (пишет `settings.json`)
и `claude mcp add` (пишет `.claude.json`), запущенные внутри профиля:

| | симлинк | хардлинк |
| --- | --- | --- |
| ссылка после записи | **цела** | **разорвана** (у профиля новый inode) |
| изменение видно в `~/.claude` | да | нет, общий файл остался старым |
| inode общего файла | сменился — писали именно в него | не менялся |

То есть симлинк работает ровно как задумано, а хардлинк разъехался бы на первой
же правке настроек из профиля. Плюс каталоги хардлинком не связать в принципе
(`ln: Is a directory`), а в общем списке каталогов большинство.

Тест-канарейка на это поведение лежит в `tests/` — если будущая версия Claude
Code перестанет резолвить путь, он это поймает.

Страховка на всякий случай всё равно есть: если ссылка когда-нибудь всё же
превратится в отдельный файл (сторонний редактор, ручной `cp`, смена поведения),
`claude-login doctor` покажет это как `diverged`, `claude-login relink` вернёт
ссылку молча, если копия побайтово совпадает с общей, а `relink --force` уберёт
разошедшуюся копию в `<профиль>/.shadowed/`. Без `--force` чужие данные не
трогаются.

### `.claude.json` — единственное, что не шарится напрямую

В нём лежат и общие вещи (доверенные папки, `mcpServers`, состояние онбординга),
и сам аккаунт (`oauthAccount`) — поэтому симлинком его сделать нельзя. При
создании профиля общая половина **копируется** (отключается флагом `--no-seed`),
а дальше подтягивается по требованию:

```bash
claude-login sync          # для всех профилей
claude-login sync work     # для одного
```

`sync` перезаписывает `mcpServers`, `theme`, флаги онбординга из основного
`~/.claude.json`, а `projects` **сливает**: профиль получает новые доверенные
папки, но своя пер-проектная история промптов не затирается. `oauthAccount` не
трогается никогда.

**Личным для каждого профиля остаётся:** сами креды, `oauthAccount`, сессии,
телеметрия и кеши — то есть ровно то, что привязано к аккаунту.

## Команды

```
claude-login                      список профилей, выбор стрелками, запуск claude
claude-login work                 сразу запустить claude под профилем work
claude-login work --resume        любые лишние аргументы уходят в claude
claude-login -- --model opus      то же, но профиль выбирается в списке

claude-login add                  залогинить новый аккаунт (имя возьмётся из email)
claude-login list                 таблица с лимитами и статусом токенов
claude-login list --no-usage      без похода в сеть
claude-login list --json          то же машиночитаемо
claude-login rename a@b.com job   переименовать профиль
claude-login remove a@b.com       удалить профиль и отозвать сессию
claude-login prune                убрать протухшие/битые профили
claude-login prune --dry-run      только показать, что удалилось бы
claude-login prune --stale-days 30  плюс те, которыми не пользовались 30 дней
claude-login settings             раздел настроек: флаги запуска (или `s` в списке)
claude-login flags                показать флаги запуска claude
claude-login flags -- --continue  заменить их
claude-login flags --clear        запускать claude без флагов
claude-login env work             напечатать export CLAUDE_CONFIG_DIR=...
claude-login relink               пересоздать общие симлинки
claude-login relink --force       плюс убрать разъехавшиеся копии в .shadowed/
claude-login sync                 подтянуть доверенные папки и MCP из ~/.claude.json
claude-login doctor               диагностика
```

Алиасы: `ls`→`list`, `rm`/`delete`→`remove`, `clean`→`prune`, `run`/`switch`→`use`,
`new`/`login`→`add`. Имя можно сокращать: `claude-login work` найдёт
`work@example.com`.

### Никаких имён и подписей

`claude-login add` ничего не спрашивает: открывает браузер, а после логина сам
берёт email из аккаунта и называет профиль по нему. Логин при этом идёт во
временный каталог — итоговое имя известно только после него, — а потом каталог
переезжает вместе со своим элементом Keychain. Прерванный логин не оставляет
ни профиля, ни мусора; повторно добавить уже заведённый аккаунт нельзя.

Если очень нужно другое имя каталога — `claude-login add короткое-имя`.

### Лимиты

Колонки `5H` и `WEEK` берутся из `GET /api/oauth/usage` — того же эндпоинта,
что показывает `/usage` внутри сессии. Значения всегда живые: ничего не
кешируется между запусками, потому что лимит, показывающий `4%`, когда он на
самом деле выбран, хуже отсутствия цифры. Не получилось запросить — будет `—`.

Ждать сеть при этом не приходится: список рисуется сразу (~100 мс) с
многоточием `…` в колонках лимитов, а цифры подставляются, когда придут
(~0.3–0.7 с). Клавиша `r` перезапрашивает, `--no-usage` не ходит в сеть вовсе.

Конец окна показывается всегда, а не только когда упёрлись в лимит:
`4% ⟳ 17:10`, `96% ⟳ 28.07 23:00`. У пятичасового окна выводится одно время,
если оно закрывается сегодня, и время с датой, если уже завтра.

Цвет: до 60% зелёный, до 85% жёлтый, дальше красный, на 100% — красный жирный.
Само время приглушено, чтобы первым читался процент; на 100% оно подсвечивается
вместе с ним, потому что там важно именно оно.

Если выбран **недельный** лимит, пятичасовой красится красным независимо от
своего значения: пустое пятичасовое окно ни на что не годится, пока недельное
исчерпано, и зелёные `0%` вводили бы в заблуждение.

`0% ⟳ —` значит, что пятичасовое окно ещё не открыто: оно стартует с первого
запроса, и до этого конца у него нет — API отдаёт `resets_at: null`.

`WEEK` — это общий недельный лимит. Если отдельный лимит на модель (Opus, Fable)
уже выбран, а общий ещё нет, он дописывается рядом:
`96% ⟳ 28.07 23:00 · Fable 100%` — иначе аккаунт выглядел бы рабочим, хотя нужная
модель уже недоступна. Время у него печатается, только если отличается от общего.

Если у аккаунта протух access-токен (живёт ~8 часов), он обновляется через
`POST /v1/oauth/token` — ровно как это делает сам Claude Code, — и новые токены
записываются обратно. Обновление происходит **только** когда токен реально
истёк: валидный используется как есть, чтобы не устроить гонку с работающей
сессией. Побочный полезный эффект — редко используемый аккаунт не протухает.

Запросы ко всем аккаунтам идут параллельно, в потоках. Asyncio тут ничего не
даёт — замер показал, что запросы и так шли внахлёст, а лишнее время съедал
`urllib.request`, который на каждый вызов собирает цепочку обработчиков.
Переход на `http.client` дал 410 → 275 мс на трёх аккаунтах; asyncio на сырых
сокетах — 294 мс, то есть неотличимо от потоков.

HTTP/3 недоступен: `api.anthropic.com` не отдаёт заголовок `alt-svc`, то есть
QUIC не анонсирует вообще, а ALPN согласует `h2` поверх TLS 1.3. Да он бы и не
помог — в разбивке одного запроса (DNS 2 мс, TCP 80 мс, TLS 78 мс, **TTFB
436 мс**, тело 0 мс) сэкономить можно было бы только TLS-рукопожатие, ~13% от
общего времени. Мультиплексирование HTTP/2 тоже не дало бы ничего по
времени: три рукопожатия и так идут одновременно, в трёх потоках. 73% времени —
это ответ `api.anthropic.com`, и на него ускорение клиента не влияет никак.

### Аргументы запуска

В коде дефолтов нет вообще: свежее хранилище запускает `claude` без флагов.
Всё лежит в конфиге, в ключе `launchArgs` (`~/.claude-accounts/accounts.json`).

Настраивается в интерфейсе — клавиша `s` в списке аккаунтов или
`claude-login settings`:

```
Settings — launch flags

claude --dangerously-skip-permissions --continue --effort max

           SETTING                         FLAG               VALUE
❯ Skip permission prompts     --dangerously-skip-permissions  on
  Continue last conversation  --continue                      on
  Reasoning effort            --effort                        max
  Other flags                 —                               edit

↑↓ move · ⏎ change · e edit as text · c clear all · q back
```

Enter переключает строку (у `--effort` перебирает `off → low → … → max`),
верхняя строка сразу показывает получившуюся команду. `Other flags` — всё
остальное, что не разложено на переключатели.

То же из командной строки:

```bash
claude-login flags                                       # показать текущие
claude-login flags -- --effort max --continue            # заменить
claude-login flags --clear                               # запускать голый claude
claude-login --no-flags work                             # разово без флагов
```

Аргументы складываются в три слоя: `launchArgs` → `extraArgs` профиля →
то, что вы набрали после имени аккаунта. Правый слой перебивает левый по имени
флага, так что `claude-login work --effort low` победит `--effort max` из
конфига, а дубля не будет. `-c` и `-r` считаются теми же флагами, что
`--continue` и `--resume`.

Флаги самого `claude-login` (`--no-flags`, `--no-usage`, `-r`) идут **до** имени
аккаунта, всё что **после** — уходит в `claude` как есть.

Постоянные аргументы для конкретного аккаунта — в его `extraArgs` там же,
например `"extraArgs": ["--model", "opus"]`.

### Автопродолжение последнего диалога

`--continue` в `launchArgs` продолжает последний диалог в текущем каталоге.

Ставить его безусловно нельзя: без транскрипта `claude --continue` не начинает
новую сессию, а **прерывает запуск** с `No conversation found to continue`
(проверено по коду и на живом бинарнике). Поэтому перед запуском проверяется,
есть ли непустой транскрипт для текущего каталога, — и если нет, флаг просто не
передаётся. Каталог вычисляется по тому же правилу, что и у Claude Code:
все не-алфанумерики в пути меняются на `-`, а путь длиннее 200 символов
обрезается и получает хвост-хеш.

`--continue` также снимается, если вы явно передали `--resume` — они конфликтуют.

Транскрипты (`projects/`) общие между аккаунтами, так что диалог продолжится
независимо от того, под какой учёткой вы его начинали.

## Очистка неактуальных

`claude-login prune` разбирает четыре случая:

| статус | что это | что делает prune |
| --- | --- | --- |
| `expired` | refresh-токен протух (обычно ~11 дней простоя) | удаляет профиль и его Keychain-элемент |
| `logged-out` | каталог есть, логина нет — обычно прерванный `add` | удаляет |
| `missing` | каталог удалён руками | вычищает запись из реестра |
| orphan | каталог в `profiles/` без записи в реестре | удаляет каталог и элемент Keychain |

Без `--yes` всегда сначала показывает список и спрашивает подтверждение.
Профиль `default` (то есть `~/.claude`) prune не трогает никогда.

Токен продлевается сам при запуске `claude`, поэтому чтобы аккаунт не протух,
достаточно иногда им пользоваться. `claude-login list` заранее подсвечивает
`expires in 2d` для тех, что скоро отвалятся.

## Диагностика

```bash
claude-login doctor
```

Показывает путь к `claude`, доступность Keychain, имя Keychain-элемента для
каждого профиля, сроки жизни токенов, незалинкованные общие файлы и запущенные
процессы `claude`.

## Где что лежит

```
~/.claude-accounts/
├── accounts.json           реестр + launchArgs (0600, без секретов)
├── .registry.lock          блокировка на время записи реестра
├── .login/                 временные каталоги логина (чистятся сами)
└── profiles/
    ├── work@example.com/   CLAUDE_CONFIG_DIR этого аккаунта
    │   ├── .claude.json    свой oauthAccount
    │   ├── settings.json -> ~/.claude/settings.json
    │   └── projects      -> ~/.claude/projects
    └── me@home.com/
```

Токены в файлах реестра не хранятся: на macOS они лежат в Keychain (пишет и читает
их сам Claude Code), на других системах — в `<профиль>/.credentials.json` с правами
`0600`, как это делает Claude Code.

Переменные окружения:

| переменная | зачем |
| --- | --- |
| `CLAUDE_ACCOUNTS_HOME` | другой корень хранилища (по умолчанию `~/.claude-accounts`) |
| `CLAUDE_LOGIN_CLAUDE_BIN` | другой бинарь `claude` |
| `CLAUDE_LOGIN_API_BASE` | другой хост API (по умолчанию `https://api.anthropic.com`) |
| `CLAUDE_LOGIN_OAUTH_CLIENT_ID` | другой OAuth client_id при обновлении токена |
| `CLAUDE_LOGIN_KEYCHAIN_PREFIX` | префикс имени элемента Keychain (`Claude Code`) |
| `CLAUDE_LOGIN_OAUTH_SUFFIX` | суффикс `OAUTH_FILE_SUFFIX` из сборки Claude Code |
| `HTTPS_PROXY` | прокси для запросов лимитов |
| `NO_COLOR` / `CLICOLOR_FORCE` | выключить / принудительно включить цвет |

`CLAUDE_LOGIN_KEYCHAIN_PREFIX` и `CLAUDE_LOGIN_OAUTH_SUFFIX` нужны, только если
Claude Code сменит схему именования элементов Keychain — тогда её можно
подкрутить, не трогая код.

## Секреты

Своего хранилища секретов у `claude-login` нет: логинится настоящий `claude`, он
же пишет и читает токены. Утилита только показывает `claude` другой
`CLAUDE_CONFIG_DIR`.

Там, где токены всё-таки проходят через код (обновление протухшего access-токена
и перенос элемента Keychain при переименовании профиля):

- в `security(1)` секрет уходит **через stdin** (`security -i`), а не аргументом
  командной строки — иначе он был бы виден в `ps` любому процессу пользователя.
  Единственное исключение — блоб длиннее 4032 байт: `security -i` читает по
  команде на строку и такую строку уже не примет, тогда работает откат на argv.
  Это ровно то же поведение и тот же порог, что у самого Claude Code;
- `accounts.json` и `.credentials.json` создаются с правами `0600`, каталоги
  хранилища — `0700`;
- значения токенов не печатаются никуда и ни в каком виде: `list`, `doctor` и
  `--json` показывают только срок жизни и статус;
- в самом реестре токенов нет вообще: там имена профилей, пути, `launchArgs` и
  карточка аккаунта, которую отдаёт API, — email, UUID, организация, тариф.
  Персональное, но не секретное; `0600` тут именно поэтому.

Само хранилище лежит в `~/.claude-accounts`, за пределами репозитория, так что
в коммит ничего личного не попадает.

`client_id` в коде (`9d1c250a-…`) — не секрет: это публичный идентификатор
OAuth-клиента Claude Code, он зашит в сам бинарник и одинаков у всех.

## Тесты

```bash
python3 -m unittest discover -s tests            # изолированно, на заглушке claude
CLAUDE_LOGIN_INTEGRATION=1 python3 -m unittest discover -s tests   # + реальный Keychain
```

Интеграционные тесты — две канарейки на поведение настоящего Claude Code:
фиктивный токен кладётся в Keychain под вычисленным нами именем и проверяется,
что `claude auth status` его видит (формула имени элемента не разошлась); и что
запись `settings.json` не превращает симлинк в отдельный файл.

## Ограничения

- Переключение через Keychain — macOS. На Linux работает тот же механизм через
  `<профиль>/.credentials.json`.
- Общий `history.jsonl` дописывается всеми профилями сразу; если это мешает,
  уберите его из `shared` и сделайте `claude-login relink`.
- Уже запущенная сессия `claude` продолжает работать под своим аккаунтом —
  переключение действует на новые запуски.
- При запуске из окружения убираются `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`
  и `CLAUDE_CODE_OAUTH_TOKEN` — иначе они перебили бы выбранный OAuth-аккаунт.
- `list` печатается один раз, поэтому ждёт сеть (6 с таймаут, параллельно);
  интерактивный список — нет, он рисуется сразу. `--no-usage` отключает
  обращение к сети полностью.
